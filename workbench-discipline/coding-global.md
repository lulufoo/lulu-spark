# AI Coding — 全局编码约束

> 基于 [Andrej Karpathy 的观察](https://x.com/karpathy/status/2015883857489522876)，
> 由 [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills) 整理。
> 适用于所有语言的编码任务。

**权衡说明**：这些原则偏向**谨慎而非速度**。对于显而易见的简单改动，自行判断是否需要完整流程。

---

## 原则 1：编码前先思考

**不要假设。不要隐藏困惑。呈现权衡。**

实现之前：
- 明确说明你的假设。不确定时，提问而不是猜测。
- 如果存在多种合理解读，全部列出——不要默默选一个执行。
- 如果有更简单的方法，说出来。该反驳时反驳。
- 如果有不清楚的地方，停下来。指出困惑点，要求澄清。

---

## 原则 2：简洁优先

**用最少的代码解决问题。不做推测性实现。**

- 不添加需求之外的功能。
- 不为一次性代码创建抽象层。
- 不添加未被要求的「灵活性」或「可配置性」。
- 不为不可能发生的场景写错误处理。
- 如果 200 行能压缩为 50 行，重写它。

**检验标准**：资深工程师会觉得这过于复杂吗？如果是，简化。

---

## 原则 3：精准修改

**只碰必须碰的代码。只清理自己造成的混乱。**

编辑现有代码时：
- 不要「顺手改进」相邻代码、注释或格式。
- 不要重构没坏的东西。
- 匹配现有代码风格，即使你更倾向于不同写法。
- 如果注意到无关的死代码，提一下——不要删除它。

当你的改动产生孤儿代码时：
- 删除**因你的改动**而变得无用的 import / 变量 / 函数。
- 不删除预先存在的死代码，除非被明确要求。

**检验标准**：每一行修改都应该能直接追溯到用户的请求。

---

## 原则 4：目标驱动执行

**定义成功标准，循环验证直到达成。**

将指令式任务转化为可验证的目标：

| 不要这样 | 转化为 |
|---------|--------|
| 「添加验证」 | 「为无效输入写测试，然后让测试通过」 |
| 「修复 bug」 | 「写出能复现 bug 的测试，然后让测试通过」 |
| 「重构 X」 | 「确保重构前后测试都能通过」 |

多步骤任务，先说计划：

```
1. [步骤] → 验证：[检查点]
2. [步骤] → 验证：[检查点]
3. [步骤] → 验证：[检查点]
```

明确的成功标准让 AI 能独立循环执行。模糊标准（「让它能跑」）需要不断澄清。

---

> 原则 1–4 约束编码行为；原则 5 是执行中的强制退出条件。

## 原则 5：证据优先

**只执行被明确要求的操作，其余一律不做。**

执行过程中，遇到以下任一情况，立即停止并列出问题，禁止继续生成代码：

1. 需要变更但施工单未明确要求的代码或配置
2. 需要调用但用法或边界无法查证的 API
3. 需要引入但未被明确要求的依赖
4. 需要推断才能继续的决策点

---

## 效果验证

以下迹象说明这些原则正在发挥作用：
- diff 里不再出现未被要求的改动
- 第一次就写出简洁的代码，而不是事后重写
- 澄清问题在实现之前提出，而不是犯错之后
