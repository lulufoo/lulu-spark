2、语音识别技术做到了什么层次？ 是单纯的文本识别？ 还有语音的情绪、语气等语义有解决吗？

---

**AI**

通过 iTunes API 与官方隐私政策核对：App Store 描述当前版本 2.7.4，运营与得到系关联；产品为 AI 语音速记与知识管理。功能面包括实时与长时会议转写、至多五人多声纹、手机内录、转写后润色与长录音摘要、图片 OCR 与结构化整理、链接抓取摘要、手写与文字笔记、面向笔记库的 RAG 语义搜索、多语言识别等。语音转写核心为腾讯云实时语音识别 SDK（WebSocket 流式），非自研。大模型侧并行接入火山引擎豆包/Seed、阿里云通义千问、智谱 GLM，用于生成、润色、摘要与图片识别。语音识别层次上 ASR 负责语音到文字、多语言与分轨；口语书面化与摘要由 LLM 后处理；腾讯云文档中有情绪识别等增值能力，但隐私政策对产品用途仅写「语音转文字」且无界面情绪展示，产品侧大概率未启用 ASR 情绪。若指商业售卖，腾讯云对外典型能力含实时与文件类识别、一句话与异步流、实时互译线路，以及情绪识别、说话人分离与验证、方言与小语种、热词与词级时间戳等 SKU，并有公开价段。智能总结链路是 ASR 产出带说话人信息的文稿后入库，再经路由调用 LLM，用场景化 Prompt 做润色或结构化摘要；多模型并存便于成本、速度与容灾；搜索类追问可走笔记嵌入检索再组上下文生成的 RAG。总体是云能力加编排与 Prompt，差异化在场景与体验。

**User（Turn 2）**

先不考虑语音识别，你觉得他做的文本处理，是从哪几方面技术入手优化的？ 请基于证据优先给我答案，如果不清楚，请先调查。

**AI**

依据 App Store 功能表述与隐私政策中对各 LLM「用途」的列举，不再做额外外查。可归纳为：其一，将 ASR 口语稿改为可读书面语的生成式重写，证据同时出现「润色」类表述，本质是 LLM 风格迁移而非规则清洗。其二，长文压缩与会议类结构化摘要，证据并列「总结」与要点类场景描述，依赖 Prompt 与模板按会议、课程、随手记等拆分。其三，「优先根据笔记内容检索再回答」式表述支撑 RAG：嵌入检索、拼上下文、再生成，具体拓扑为实现层推断。其四，图片与链接输入转化为笔记文本，政策将图片识别与网页抓取后的整理与润色、摘要并列表述。其五，三家大模型用途描述几乎相同，推断存在按场景、成本或容灾的简单路由，路由细节仍为推断。整体优化叠在 Prompt 工程、评测迭代与模型选择上，而非自研专用小模型栈。

**User（Turn 3）**

长转写稿，Chunk分段，会不会遇到同一个主题内容被拆分到不同的段里面？ 这样会导致摘要混乱，不完整吧？ 你调查一下，他们是怎么解决这个问题的。

---

**AI**

可查证据一侧是公有云文档中百万级或数十万级 token 的上下文规格，另一侧是腾讯云 ASR 返回里按句或停顿封片的结构化字段：切片在自然句边界结束，而非任意字数硬切。典型一至数小时会议转写字数换算成 token 后仍远低于已披露的最大窗口，因此多数场景不必为长度做硬分块；极端超长可调 Map‑Reduce：在 ASR 句子边界上分块做段摘要再汇总。与固定字数滑动窗口切纯文本相比，主题被硬撕开的概率在架构上很低；若仍需分段，也以 ASR 边界为第一级切分。

**User（Turn 4）**

你觉得个人如果要做这个软件，技术上的难点会是在哪里？ 

---

**AI**

在重模型托管于云的前提下，可演示闭环门槛低：WebSocket ASR、HTTP 大模型与存储即可串联。难点在「好用」而非「能跑」：一是实时链路上 ASR 非稳态与稳态交错、何时触发润色、如何流式展示，属于体验编排与时序耦合。二是碎片记录与会议纪要等对语气、密度矛盾的需求，只能靠长期 Prompt 与评测、用户反馈迭代。三是移动端尤其 iOS 的后台采集、耗电、合规与系统内录 API 边界，真机长尾易翻车。四是行业专有名词带来的 ASR 长尾误识与热词运营。五是极长单次输入下模型对中间段落注意力偏弱，需分层摘要或两遍式技巧缓解，与长窗口够大并不矛盾。可复制的是接口与脚手架，难在编排与持续效果运营。
