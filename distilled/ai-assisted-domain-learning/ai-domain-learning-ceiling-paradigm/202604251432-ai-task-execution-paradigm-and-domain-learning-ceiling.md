## 本次对话在追什么

对话从一个具体观察出发——单 .md 文件执行任务，DDM 的 Phase 4 被跳过——追问这背后的结构性原因，进而建立了一个清晰的框架：prompt 范式 vs 代码调度范式，以及领域知识密度 vs 推理架构能力这两个独立的天花板：

- 转折 1：多文件拆分是人类作者的组织工具，不改变 LLM 执行的范式
- 转折 2：MD 驱动和 LangGraph 的根本区别是"谁负责调度执行"，领域知识都仍在 prose 里
- 转折 3：meta-agent 面临的是"元领域理解"的递归瓶颈，只对通用模型覆盖良好的领域可行
- 转折 4：DP_1 框架的天花板是知识密度，而不是流程约束
- 转折 5：知识密度和推理架构能力是两个独立瓶颈，作用在不同步骤上；结构重组是质变问题，不是量变问题

## 单 .md 文件执行 = 仍是 prompt 范式

从 DDM Phase 4 被跳过这个现象追问：为什么会被跳过？

原因在于 .md 文件被读进上下文后，LLM 在一次生成中"顺着"这段文本推进——没有真实的控制流、没有阶段 gate、没有状态机。有的只是"LLM 读到这段文字后倾向于怎么做"。Phase 4 被跳过，不会触发任何错误，只有输出缺失。在代码里，任何一步缺失都会报错；在 prompt 里，不会。

多文件拆分（如 DDM 各 Phase 分文件）解决的是**人类作者的组织问题**，不是 **LLM 执行的可靠性问题**。LLM 执行时，两个文件最终都被展平进同一个上下文，执行模型没有本质变化。多文件 ≠ 多模块，只要还是读文本→生成，就仍是 prompt 范式。

真正能解决 Phase 4 跳过的是代码调度：把"执行流程"从 prose 里拿出来，用代码显式定义，LLM 只负责每个节点内的策略判断，而不是同时负责执行调度。当前 DDM 加了"Phase 4 完成标志"是在结构化 prompt 内部能做到的极限——提高了概率，但没有改变范式。

```
纯 prompt → 结构化 prompt（DDM 现状）→ prompt + 代码调度（LangGraph）→ 纯代码
可读性强 ←————————————————————————————————————→ 执行可靠性强
```

## MD 驱动 vs LangGraph：根本区别只有一个

你提出两种任务流实现思路都是"DDD 领域驱动范式"——这个类比部分成立，但核心区分维度更简单：**谁负责调度执行？**

| | MD 驱动 | LangGraph |
|---|---|---|
| 领域知识载体 | Prose（.md） | Prose（每个节点的 prompt） |
| 流程框架定义者 | .md 里的 Phase 描述 | 代码里的状态机 |
| 调度执行者 | LLM（读文本后自行决定推进） | 代码（显式状态机）|
| 流程可靠性 | 概率性 | 确定性 |

两种方式**领域知识都仍在 prose 里**，差别只是"谁来决定下一步执行什么"。LangGraph 固化的是流程拓扑，不是领域模型本身——"将领域模型定义到代码里"这个表述需要修正。

当任务步骤增多、分支增多，MD 驱动的问题不是"MD 写得不够好"，而是：LLM 同时负责**策略判断**和**调度决策**，两件事的错误会叠加。代码调度之后，错误不叠加。这是**不可通过改写 prompt 跨越的结构差异**。

## meta-agent 的递归瓶颈

你将这个框架延伸到 meta-agent——自动生成领域 Agent 的 Agent，本质是"领域模型变成 Spec 的需求"。

这个推导引出了一个递归问题：meta-agent 要生成"能理解某领域的 Agent"，它自己必须先理解那个领域，且知识密度要求不是线性叠加，而是递归叠加。

你的判断是准确的：meta-agent 只能可靠解决"基础模型已覆盖"的领域，而不是"复杂度低"的领域——判断标准需要修正为**基础模型的领域知识密度**，而非复杂度。

真实的专域 Agent 落地路径是：专域预训练模型 → 人工设计的领域工作流（不是 meta-agent 生成的）→ LLM 节点在各环节执行局部推理。"模型专门化"和"Agent 专门化"不总是同时需要：金融交易只需 Agent 层固化流程，医疗诊断则需两者同时。

## DP_1 框架的真实天花板

把这个框架拉回到 DP_1（领域深化框架）：它的天花板在哪里？

用三个维度分析：

| 瓶颈维度 | DP_1 里的具体表现 |
|---------|-----------------|
| **知识密度** | 关键点识别和深挖的质量完全取决于 LLM 对该领域的覆盖。窗帘制造：LLM 知道遮光率，但不知道工厂的原料供应商结构、品控卡点、定制订单报价逻辑 |
| **推理架构能力** | 结构重组需要元认知推理——LLM 容易把错误结构维持下去而不触发重组信号 |
| **流程约束** | DP_1 每步错误可在下轮修正，无跨会话状态，无合规强制，**不满足引入 LangGraph 的任何门槛** |

通用 Agent 读 MD 驱动对 DP_1 完全足够——**DP_1 的当务之急是解决知识输入问题（RAG/文档注入），而不是流程约束问题。**

---

## 知识密度和推理架构能力是两个独立瓶颈

你质疑了"深挖节点需要推理架构能力"的说法，指出知识密度够了子概念边界自然浮现，不需要额外推理能力——这个质疑是准确的。

修正后两个瓶颈作用在不同步骤上：

| DP_1 操作 | 知识密度依赖 | 推理架构能力依赖 |
|-----------|------------|----------------|
| 识别关键点 | 高 | 低 |
| 深挖单个节点 | **极高** | 低（子概念边界在知识里，不在推理里）|
| 放入结构（归类） | 低 | 高 |
| 触发结构重组 | 低 | **极高** |
| 输出图谱 | 低 | 中 |

这也引出了最后一个区分：**推理架构能力的天花板是质变问题，不是量变问题**。

深挖节点（多展开几层）类似于"100 个数字加法 vs 10000 个数字加法"——给更多 token（CoT、extended thinking）有帮助。

结构重组则类似于"加法 vs 高阶导数"——LLM 用来判断"结构是否合理"的标准，和它用来"建立这个结构"的标准，来自同一套权重。多给 token，LLM 会在错误框架内推得更深更自洽，反而强化错误。这是 human-in-the-loop 在结构重组环节有效的原因：人类提供的是**框架外的视角**，不是同一套权重下的更深计算。
