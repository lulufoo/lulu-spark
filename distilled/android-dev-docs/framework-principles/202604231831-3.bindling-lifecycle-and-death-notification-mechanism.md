## bindService 从发起到回调的完整链路

起点是这样一个认识：Service 是 Android 四大组件之一，是跨进程通信的手段，Client 通过 bindService 绑定 Server 端的服务，底层通过 AMS 作为桥梁。

那从 Client 调用 bindService 开始，到底发生了什么？

Client 先通过 ServiceManager 获取 AMS 的 Binder，然后经由这个 Binder 调用 AMS 的 bindService 接口。AMS 收到请求后，先查缓存——如果这个 Service 已经被 bind 过，有缓存的 IBinder，直接返回。如果没有，AMS 通过 PackageManagerService 解析目标 Service 信息。此时如果 Server 进程不存在，先启动进程。进程启动后 attach 到 AMS，AMS 通过 IApplicationThread 调用 scheduleCreateService，Server 创建 Service 实例并执行 onBind()，返回一个 IBinder 对象。AMS 缓存这个 IBinder，然后通过 Client 传入的 IServiceConnection 接口回调，最终触发 Client 代码里写的 `ServiceConnection.onServiceConnected()`。

这里有个细节值得注意：开发者写的 `ServiceConnection` 和传给 AMS 的 `IServiceConnection` 不是同一个对象。`IServiceConnection` 是 Framework 内部构造的 Binder，它负责接收 AMS 的回调，再转发给开发者写的 `ServiceConnection`。这层封装的具体实现本次没有深入。

## onBind 返回值的缓存机制与 onUnbind 的触发时机

一个自然的疑问是：onBind() 每次 bind 都会被调用吗？能不能每次返回一个新的 IBinder？

直觉上觉得可以——onBind() 是你自己写的，每次 new 一个新对象 Framework 不会拦。但实际上 AMS 的缓存逻辑决定了：第一次 onBind() 返回的 IBinder 会被缓存，后续同一个 Intent 的绑定请求直接走缓存，**onBind() 不会被再次调用**。所以即使代码里每次 new，第二个 Client 拿到的还是第一次那个。判断依据是 Intent 是否匹配同一个 Service 实例，不是 Client 的身份。

反过来看 unbind：如果进程 A 和 B 都绑定了同一个 Service，A 调了 unbindService，Service 会销毁吗？

答案是不会。AMS 维护绑定引用——每次 bind 加一，每次 unbind 减一。只有当所有绑定都断开（归零），AMS 才调 onUnbind()，然后销毁 Service（onDestroy）。但如果 Service 同时被 startService 启动过，归零后也不销毁，还需要额外 stopService。

所以 onUnbind 不是"每次 unbind 都触发"，而是"最后一个绑定断开时才触发"。

## 进程死亡时的感知机制

Client 进程如果意外崩溃（不是主动 unbindService），AMS 还能正确清理吗？

一个关键的联想是 `linkToDeath`——Binder 提供的死亡监听机制。直觉上，Client 崩溃 AMS 应该能感知并通知 Server，Server 崩溃也应该通知 Client。这个方向是对的。

### 最初的理解偏差

最初以为 AMS 在每次 bindService 时，对 Client 传入的 IServiceConnection 调 linkToDeath——也就是每次 bind 都注册一次。如果 Client bind 了多个 Service，就有多个 linkToDeath，Binder 驱动就要通知多次。

实际不是这样。**AMS 只在进程 attach 时，对 IApplicationThread 注册唯一一个 DeathRecipient**：

```java
// ProcessRecord.java
private IBinder.DeathRecipient mDeathRecipient;
// 挂在 mThread.asBinder() 上，整个进程只有一个
```

IApplicationThread 代表整个进程的存活凭证。一个进程只有一个 IApplicationThread，所以只有一个 linkToDeath，Binder 驱动只发一次死亡通知。

### Client 死亡后的批量清理路径

死亡通知到来后，AMS 拿到的是整个 ProcessRecord。ProcessRecord 持有该进程作为 Client 建立的所有 ConnectionRecord，在一次 `appDiedLocked()` 调用中遍历全部清理：

```
进程 attach AMS → linkToDeath(IApplicationThread)   ← 唯一一次
bindService A → 建立 ConnectionRecord_A（不额外 linkToDeath）
bindService B → 建立 ConnectionRecord_B（不额外 linkToDeath）
→ Client 死亡 → Binder 驱动通知一次
              → appDiedLocked(ProcessRecord)
              → 遍历该进程所有 ConnectionRecord，批量清理
```

这个设计的好处：死亡监听代价恒为 O(1)，清理是 O(n) 遍历。

## AMS 内部的映射数据结构与反向查找

进一步追问：AMS 收到死亡通知后，怎么从 ConnectionRecord 找到对应的 ServiceRecord 去做清理？

最初对"反向查找"理解不够清楚——以为需要某种查询表。实际上是直接的字段引用：

```
ServiceRecord
  └── bindings: ArrayMap<Intent, IntentBindRecord>
        └── IntentBindRecord
              └── apps: ArrayMap<ProcessRecord, AppBindRecord>
                    └── AppBindRecord
                          └── connections: ArraySet<ConnectionRecord>
                                └── ConnectionRecord
                                      ├── conn (IServiceConnection)
                                      └── binding → AppBindRecord（反向引用）
```

反向路径一步到位：`ConnectionRecord.binding → AppBindRecord`，`AppBindRecord.service → ServiceRecord`。

"引用计数"的本质不是整型计数器，而是 `ServiceRecord.connections` 这张表的条目数。所有 ConnectionRecord 清空后，检查 `IntentBindRecord.hasBound`（布尔标记，记录是否曾调用过 onBind），如果为 true 则触发 onUnbind。

IBinder 对象（onBind() 返回的）缓存在 `IntentBindRecord.binder` 字段中。

## Server 进程死亡时 AMS 的主动通知

反过来看：Server 进程死亡时，AMS 怎么处理？最初的猜想是"拿到所有 ServiceRecord 然后 remove 就行"，或者"Client 自己注册了 linkToDeath，自己会收到通知"。

实际上只 remove 不够。AMS 会**主动通知** Client：

1. 遍历 `ServiceRecord.connections`，对每个 ConnectionRecord 调用 `conn.connected(name, null, dead=true)` 通知 Client
2. 将 `ConnectionRecord.serviceDead` 置为 true
3. 如果满足重启条件，安排 Service 重启
4. 清理记录

Client 侧收到 `dead=true` 后：

```java
// LoadedApk.java doConnected()
if (dead) {
    mConnection.onBindingDied(name);   // Server 已死亡
}
// 同时还会触发：
mConnection.onServiceDisconnected(name);
```

所以 Server 死亡时，Client 会同时收到 `onServiceDisconnected()` 和 `onBindingDied()`。Client 自己的 linkToDeath（注册在 onBind 返回的 IBinder 上）是第二条路径，Framework 做了去重保护。

Service 实例与 ServiceRecord 一一对应，关联凭证是 ServiceRecord 本身——它继承自 Binder，在 `scheduleCreateService(token)` 时作为 token 传给 Server 进程。

```
Server 进程死亡
    │
    ▼
AMS appDiedLocked(ProcessRecord_Server)
    │
    ├── ProcessServiceRecord.mServices → 遍历所有 ServiceRecord
    │       └── ServiceRecord.connections → 遍历所有 ConnectionRecord
    │               └── conn.connected(name, null, dead=true)
    │                       → Client: onServiceDisconnected() + onBindingDied()
    │
    └── 清理 ServiceRecord、决定是否重启
```

## 统一设计：IApplicationThread 作为进程存活凭证

最终收敛到一个核心认识：**IApplicationThread 代表的是整个进程的存活凭证**。进程 attach AMS 时注册这一个 DeathRecipient，AMS 就拥有了对该进程生命周期的完整掌控。这个设计不只服务于 bindService——Activity 栈清理、ContentProvider 连接断开、BroadcastReceiver 超时取消，全部走同一条 `appDiedLocked()` 路径。
