## 一、mmap 在 Binder 中解决的是什么问题

最初的理解是：mmap 是 Binder 使用的内存技术，可以优化内存访问效率。这个方向是对的，但"优化效率"太模糊——具体优化的是什么？

从没有 mmap 的情况出发推导：

1. 发送进程把数据从用户空间拷贝到内核空间（`copy_from_user`）
2. 如果没有 mmap，内核还需要把数据再次拷贝到接收进程的用户空间（`copy_to_user`）
3. 也就是说，没有 mmap 的话，一次 IPC 需要两次内存拷贝

mmap 省掉的是第二次拷贝。省掉的方式是：让接收进程的用户空间和内核缓冲区映射到同一块物理内存。接收进程不需要等数据拷过来，直接读那块物理内存即可。

---

## 二、映射关系的精确定位

自然的第一反应是：mmap 让"发送进程和接收进程共享一块用户空间内存"。这个理解是错的，需要校准。

Binder mmap 的映射关系是：

> **接收进程的用户空间** ↔ **内核缓冲区** → 同一块物理页

发送进程不参与 mmap 映射。它只做一件事：通过 `copy_from_user` 把数据从自己的用户空间推进内核缓冲区，之后就失去控制权。

为什么发送进程不需要映射？因为它的角色是"推数据进去"，不是"读数据出来"。mmap 的价值在接收端，省掉的是接收端那次拷贝。

---

## 三、映射在什么时候建立

直觉是"获取 Binder 实例时触发映射"，但这个时机还不够早。

实际时机是进程初始化阶段：

```
open("/dev/binder")  →  mmap()  →  映射建立完成
```

进程在加入 Binder 通信体系时，就已经一次性分配好内核缓冲区，并把它映射到自己的用户空间。后续每次 IPC 都复用这块已映射的区域，不会每次重新建立映射。

这意味着：**每个进程都有自己的 mmap 区域**，因为任何进程都可能成为接收方。"发送方"和"接收方"只是某次 IPC 中的角色，不是固定身份。

---

## 四、内核如何管理这块缓冲区

这块 ~1MB 的区域需要服务多个并发的 IPC 请求，内核要追踪哪些区域已分配、哪些空闲。

Binder 驱动使用**两棵红黑树**来管理：

- 一棵记录**空闲块**，按大小排序
- 一棵记录**已分配块**，按地址排序

每次 IPC 进来，驱动在空闲树里做 best-fit 查找，找到最小的能容纳本次数据的块，切割分配。

数据传输完成、接收方处理完毕后，接收进程必须主动发送 `BC_FREE_BUFFER` 命令，通知驱动回收这块区域。如果不主动释放，1MB 的空间会被慢慢耗尽。

---

## 五、完整的一次 IPC 数据流

```
[Step 1] 接收进程初始化
         open("/dev/binder") + mmap()
         → 内核分配 ~1MB 缓冲区
         → 建立"接收进程用户空间 ↔ 内核缓冲区"的物理页映射

[Step 2] 发送进程发起调用
         copy_from_user()
         → 数据从发送进程用户空间写入接收进程的内核缓冲区（物理页 A → 物理页 B）

[Step 3] 接收进程读取数据
         直接通过用户空间 mmap 地址访问物理页 B
         → 无需第二次拷贝

[Step 4] 接收进程处理完毕
         发送 BC_FREE_BUFFER
         → 驱动将该块从已分配树移回空闲树
```

mmap 在 Step 1 建立，在 Step 3 发挥作用，在 Step 4 完成生命周期。

---

## 六、为什么不让发送方和接收方直接共享用户空间内存

一个自然的替代方案：让两个进程共享同一块用户空间内存（类似 POSIX shared memory），这样连 `copy_from_user` 也省了。Binder 没有走这条路，核心原因是**安全性**。

如果发送方和接收方共享同一块用户空间内存，发送方在写入之后仍然持有写权限，可以在接收方读取过程中篡改数据。这是经典的 TOCTOU（Time-of-Check-Time-of-Use）攻击面。

Binder 的设计通过"让内核成为唯一的写入控制者"在结构上消除了这个问题：

> 发送方通过 `copy_from_user` 把数据交给内核后，就失去了对这块数据的控制权。接收方读到的内容，发送方无法再修改。

这个规律在其他 IPC 机制中也有体现：管道、Socket、消息队列都让内核成为数据过境的唯一管道，发送方写完即失控。

---

## 七、大块数据传输：零拷贝路径

Binder 的 1MB 限制加上 `copy_from_user` 的一次拷贝，在大块数据场景（图片、视频帧）下代价较高。

这里主动推导出了另一条路：让发送方在内核直接创建内存，发送方和接收方都从用户空间直接映射同一块物理内存——零拷贝。

这正是 **`ashmem` / `ASharedMemory` / `memfd`** 的机制。大块数据走这条路：

1. 发送方创建匿名共享内存，得到一个 fd
2. 通过 Binder 把 fd 传给接收方（fd 本身很小，走普通 Binder 传输）
3. 接收方 `mmap` 这个 fd，直接映射同一块物理页
4. 双方都能读写，无任何拷贝

代价是安全性降低：发送方保留写权限，TOCTOU 风险仍然存在，需要调用方自律。

---

## 八、两种机制的选型边界

两种机制是互补关系，不是替代关系：

| 维度 | Binder 传输 | 共享内存（ashmem/memfd） |
|------|------------|--------------------------|
| 交互模式 | CS 调用，有请求/响应语义 | 数据共享，无调用语义 |
| 数据生命周期 | 短暂，传完即释放 | 明确，由双方协商控制 |
| 数据可变性 | 内核写入后发送方失控 | 双方可读写（需自行同步） |
| 安全隔离 | 内核强保证 | 依赖调用方自律 |
| 数据规模 | 小块、高频 | 大块、低频或持续共享 |

选型原则：**CS 结构、需要强隔离、小块高频数据 → Binder；数据本身是多个进程共享的不可变实体、大块 → 共享内存传 fd**。

## 九、Linux 内存映射基础：理解"物理页共享"的前提

对话中出现了一个核心疑问：`copy_from_user` 到底把数据从哪里拷到哪里？接收方的"直接映射"是跳过了什么？

理解这些需要一个最小的 Linux 内存映射模型。

每个进程看到的内存地址是**虚拟地址**，不是真实物理地址。内核通过**页表**维护"虚拟地址 → 物理地址"的映射：

```
进程 A 虚拟地址 0x7fff0000  ──页表A──▶  物理页 #100
进程 B 虚拟地址 0x7fff0000  ──页表B──▶  物理页 #300  （不同物理页）
```

两个进程可以有相同的虚拟地址，但映射到不同物理页，互不干扰。

**`copy_from_user` 的本质**：内核同时持有两边的映射权，直接把物理页 #100 的内容搬到物理页 #200（Binder 缓冲区）。是真实的物理内存拷贝。

**`mmap` 的本质**：不是"跳过原有映射"，而是在接收方的页表里**新增一条记录**，让接收方某段虚拟地址也指向物理页 #200：

```
内核虚拟地址  ──内核页表──▶  物理页 #200（Binder 缓冲区）
                                    ▲
接收方虚拟地址  ──接收方页表（mmap 新增）──┘
```

物理页 #200 同时出现在两张页表里。没有发生拷贝，只是"加了一条页表记录"。

用一句话总结整个过程：

> `copy_from_user`：物理页 #100 → 物理页 #200（一次真实拷贝）
> `mmap`：接收方页表登记"虚拟地址 X → 物理页 #200"（零拷贝，只改页表）

## 附录：一张最小模型图

你可以把 Binder 这里的关系想成这样：

```
发送进程用户虚拟地址  ──页表──▶ 物理页 A
                                   │
copy_from_user                     │ 真实拷贝
                                   ▼
接收端 Binder 物理缓冲页 B ◀──内核虚拟地址
           ▲
           │
接收进程用户虚拟地址 ──页表──▶ 物理页 B
```

关键点：

- 发送方数据原本在物理页 A
- 内核拷贝到 Binder 缓冲物理页 B
- 内核自己能通过内核虚拟地址访问页 B
- 接收方通过 mmap 后，也能通过用户虚拟地址访问页 B
- 所以接收方不是“访问内核地址”，而是访问自己用户空间里的一个虚拟地址，这个地址映射到了与内核相同的物理页。
