## Agentic Coding 与 Harness Engineering 的关系

不是同一个意思，但有重叠。可以这样理解：

---

### 各自的定义

**Agentic Coding**
AI Agent 自主完成编码任务的工作方式。Agent 能够：
- 理解需求 → 拆解任务 → 写代码 → 执行 → 验证 → 迭代
- 在没有人逐步指令的情况下，自主完成一个完整的开发闭环
- 代表工具：Copilot Workspace、Devin、SWE-agent

**Harness Engineering**
为 AI Agent 构建"约束框架/执行环境"的工程工作。核心问题是：
- 如何给 Agent 提供工具（Tool Use）
- 如何限制 Agent 的行为边界（Sandbox、权限管控）
- 如何设计任务输入/输出的结构（Prompt Engineering at system level）
- 如何评估 Agent 的执行质量（Eval Harness）

---

### 两者的关系

```
Harness Engineering
        ↓  提供运行环境和约束框架
Agentic Coding
        ↓  在框架内自主完成编码任务
```

| 维度 | Agentic Coding | Harness Engineering |
|------|---------------|---------------------|
| 视角 | Agent 做什么 | 人/系统如何管控 Agent |
| 关注点 | 任务自主完成能力 | 工具、沙箱、评估、约束 |
| 主语 | AI Agent | 工程师/平台 |
| 典型产出 | 可运行的代码/PR | 测试框架、工具链、执行环境 |

---

### 一句话总结

**Agentic Coding 是"Agent 在做什么"，Harness Engineering 是"人在为 Agent 搭什么舞台"。** 后者是前者得以可靠运行的工程基础，但两个词描述的是不同层次的概念，不可互换。

---

> **值得质疑的地方**：Harness Engineering 目前并不是一个完全标准化的术语，不同团队对它的定义边界不同。有人把它等同于 Eval Framework（评估框架），有人把它扩展到整个 Agent 基础设施。你看到这个词是在什么语境下出现的？不同来源可能含义有偏差。

## 长期视角：Harness Engineering vs Agentic Coding 的技术壁垒与未来走向

---

### 1. Harness Engineering 能成为技术壁垒吗？

**短期（1–3年）：是，且壁垒较高**

原因：
- Agent 行为不可预测，需要大量工程约束才能在生产环境可靠运行
- Eval Harness（评估框架）的设计需要深度领域知识 + 工程经验
- 工具链设计（Tool Design）直接影响 Agent 能力上限，非通用技能

**长期（5年+）：壁垒会被侵蚀**

风险点：
- 平台化趋势明显——AWS、Azure、Google 会将 Harness 能力产品化，变成"配置"而非"工程"
- LLM 自身能力提升后，对 Harness 的依赖会减少（后面详述）
- 标准化一旦形成，先发优势消失

> **合理质疑**：壁垒的本质不是"懂 Harness Engineering"，而是**对具体业务场景的 Agent 失效模式有深刻理解**。纯工具层面的 Harness 技能，护城河较浅。

---

### 2. Agentic Coding 能成为技术壁垒吗？

这里需要拆分两个主体：

| 主体 | 壁垒性质 | 长期判断 |
|------|---------|---------|
| **使用** Agentic Coding 的开发者 | 效率壁垒，不是能力壁垒 | 弱，工具普及后优势消失 |
| **构建** Agentic Coding 系统的工程师 | 系统设计壁垒 | 中等，但也面临平台化压力 |
| **评估和校正** Agent 输出的工程师 | 判断力壁垒 | **强，难以被自动化替代** |

**真正的壁垒不在于"会用 Agent 写代码"，而在于"知道 Agent 写错了什么、为什么错"。**

---

### 3. Harness Engineering 会成为标准，还是被 Agentic Coding 弱化？

这是个好问题，结论是：**两个趋势会同时发生，但节奏不同。**

```
现在          2–3年后         5年后
  │              │               │
Harness       Harness         Harness
工程门槛高    逐步标准化      部分内嵌进LLM
              平台产品化      剩余部分成为
              出现规范/协议   专业细分方向
                │               │
           Agentic Coding   Agentic Coding
           能力快速提升      能力成熟
           但仍需 Harness    自我校正能力
           兜底              增强，但未完全
                             取代 Harness
```

**Harness 不会消亡，但会收缩**——从通用工程技能变成高风险场景（金融、医疗、安全）的专业技能。

---

### 4. LLM 自身发展对两者的影响

这是最关键的变量，分三个维度：

#### 4.1 推理能力提升
- Agent 自我纠错能力增强 → **对 Harness 的外部约束需求下降**
- 但"更强的 Agent 犯更隐蔽的错误"——风险不降反升，**高质量 Harness 需求反而上移**

#### 4.2 上下文窗口扩展
- 长上下文让 Agent 可以自持更多状态 → Harness 中的状态管理模块简化
- Agentic Coding 的任务复杂度上限提高

#### 4.3 多模态 + 工具调用原生化
- LLM 原生支持工具调用（如 GPT-4o、Claude 3.5）→ **Harness 的工具集成层被内嵌进模型**
- 这直接侵蚀 Harness Engineering 的工作量

#### 综合判断

| LLM 能力方向 | 对 Harness 的影响 | 对 Agentic Coding 的影响 |
|-------------|-----------------|------------------------|
| 推理增强 | 需求收缩，但高风险场景需求上移 | 任务自主度提升 |
| 长上下文 | 状态管理简化 | 可处理更大规模任务 |
| 工具调用原生化 | 集成层被侵蚀 | 与外部系统交互能力增强 |
| 自我评估能力 | **最大冲击**，Eval Harness 价值下降 | Agent 闭环更完整 |

---

### 5. 长期建议（如果你在考虑个人技术方向）

**不建议押注"Harness Engineering"本身作为长期壁垒。**

真正值得建立的能力是：

1. **领域 × Agent 的结合判断力** —— 在你熟悉的领域里，知道 Agent 在哪里会系统性失效
2. **评估设计能力** —— 如何设计 benchmark，衡量 Agent 真实能力，这比 Harness 工具链更难被自动化
3. **Agent 系统架构思维** —— 不是配置工具，而是设计多 Agent 协作的系统边界

> **核心判断**：未来 LLM 会把大量 Harness 工程工作"吃掉"，但它吃不掉的是**对任务质量的最终判断权**。谁掌握判断标准的定义，谁就有壁垒。

### 首先，你的质疑是对的

上一轮我把"评估设计"和"Harness Engineering"做了切割，这个切割有些人为。

更准确的描述是：

```
Harness Engineering
├── 约束层（Sandbox、权限、工具边界）
├── 执行层（Tool Use、任务编排）
└── 评估层（Eval Design、Benchmark、质量度量）  ← 你说的这部分
```

评估层本来就是 Harness Engineering 的内生组成部分，不是外挂的。
我上一轮的表述有误导性，接受这个质疑。

---

### Benchmark 设计是什么？为什么难？

先说为什么这件事非平凡：

> **普通测试**：输入固定 → 输出固定 → 对比即可
> **Agent 评估**：输入固定 → 执行路径不固定 → 输出形式不固定 → 质量标准本身有争议

所以 Benchmark 设计的难点不在"跑测试"，而在**定义什么叫"好"**。

#### Benchmark 设计的核心要素

**① 任务分解（Task Decomposition）**

不能只评估最终结果，要评估中间步骤。

```
任务：修复一个有安全漏洞的登录模块

差的评估：代码能跑 → Pass
好的评估：
  ├── 是否识别出了漏洞类型？（SQL注入 vs XSS）
  ├── 修复路径是否合理？（打补丁 vs 重构）
  ├── 是否引入了新问题？
  └── 是否有测试覆盖修复点？
```

**② 失效模式分类（Failure Taxonomy）**

Agent 的失败不是二元的，需要分类：

| 失效类型 | 描述 | 评估权重 |
|---------|------|---------|
| 幻觉失效 | 输出看似合理但错误 | 高危 |
| 路径失效 | 方向正确但执行偏离 | 中危 |
| 过度执行 | 做了不该做的事 | 高危 |
| 欠执行 | 任务完成不完整 | 低危 |
| 效率失效 | 结果对但路径冗余 | 视场景 |

**③ 对抗样本设计（Adversarial Cases）**

不能只测"正常输入"，要专门设计让 Agent 容易犯错的场景：

- 需求描述模糊的任务
- 包含误导性上下文的输入
- 需要跨步骤记忆的长任务
- 工具调用返回错误时的降级行为

**④ 评分标准的可操作性（Rubric Design）**

这是最难的部分。

```
差的 Rubric：
  "代码质量好" → 谁来判断？怎么量化？

好的 Rubric：
  - 圈复杂度 < 10        → 可自动测量
  - 测试覆盖率 > 80%     → 可自动测量
  - 无已知 CVE 依赖      → 可自动测量
  - 变量命名符合规范     → 需要 LLM-as-Judge
  - 架构决策合理性       → 需要人工 + 领域专家
```

**⑤ LLM-as-Judge 的校准问题**

用另一个 LLM 来评估 Agent 输出，是目前的主流方案，但本身有偏差：

- 评估 LLM 倾向于打高分（位置偏差、冗长偏差）
- 需要设计 Calibration Set 来校准评估 LLM 本身
- 这就变成了一个递归问题：**谁来评估评估者？**

---

### "判断权"落地到技术投资——具体方向

分三个层次：

#### 层次一：评估工程能力（近期可投资，1–2年）

| 技术方向 | 具体内容 |
|---------|---------|
| Eval Framework 设计 | 熟悉 HELM、MT-Bench、SWE-Bench 等框架的设计逻辑，而不只是会用 |
| LLM-as-Judge 校准 | 理解评估偏差来源，会设计 calibration pipeline |
| 失效模式分析 | 能系统性归类 Agent 错误，而不是 case-by-case 看问题 |
| Trace 分析能力 | 读懂 Agent 的执行轨迹，判断"在哪一步判断错了" |

#### 层次二：领域 × Agent 的交叉判断力（中期，护城河最深）

这是最难被替代的部分，因为它要求：

```
领域深度（你懂这个行业/系统）
        ×
Agent 行为理解（你知道 LLM 在这类任务上的系统性偏差）
        ↓
= 你能定义这个场景里 Agent 的质量标准
```

举例：
- 一个懂代码安全的人 + Agent 行为理解 → 能设计出安全场景的 Agent Eval
- 一个懂金融合规的人 + Agent 行为理解 → 能判断 Agent 输出是否合规

**这种组合，LLM 很难自动生成，因为标准本身需要人来赋予权威性。**

#### 层次三：系统边界设计能力（长期，架构级）

| 技术方向 | 具体内容 |
|---------|---------|
| 多 Agent 协作边界 | 哪些任务该拆给多个 Agent，边界怎么划 |
| Human-in-the-loop 设计 | 在哪些决策点必须引入人工审核，怎么设计触发机制 |
| Agent 失效降级策略 | Agent 失败时系统如何 fallback，不是靠重试解决 |

---

### 一个反直觉的结论

> 未来技术人员的竞争力，**不是"我比 Agent 更会写代码"**，
> 而是**"我比其他人更清楚这个 Agent 在什么情况下不可信"**。

这种判断力的建立，需要大量真实场景的失效案例积累，不是读论文能得到的。
这也是为什么**在生产环境中部署和观察 Agent**，比单纯研究模型更有技术价值。

## QA vs 研发 的未来冲突，以及系统边界设计的技术深度

---

### Part 1：QA 和研发，谁更能胜任 Benchmark/Eval 工作？

**直接结论：会冲突，但不是零和博弈——真正的问题是两边都可能输。**

#### 为什么会冲突？

传统分工：
```
研发 → 写代码
QA  → 验证代码
```

Agent 时代的分工模糊：
```
Agent  → 写代码
研发   → 设计任务、审查输出
QA     → 评估 Agent 输出质量
         ↑
         这两件事开始高度重叠
```

当"验证 Agent 输出"和"定义 Agent 任务"变成同一件事的两面，
研发和 QA 的边界就自然消失了。

---

#### 各自的优劣势

| 维度 | 研发 | QA |
|------|------|-----|
| 理解 Agent 执行路径 | ✅ 强，懂底层实现 | ⚠️ 弱，通常是黑盒视角 |
| 设计对抗性测试用例 | ⚠️ 弱，思维惯性是"让它跑通" | ✅ 强，天然破坏性思维 |
| 失效模式分类能力 | ⚠️ 中，视个人经验 | ✅ 强，这是 QA 的核心训练 |
| 定义质量标准（Rubric） | ⚠️ 倾向技术指标，忽略业务指标 | ⚠️ 倾向业务指标，忽略技术根因 |
| Eval 框架工程实现 | ✅ 强 | ⚠️ 弱，通常依赖工具 |
| 领域业务判断力 | 视背景 | 视背景 |

**没有一方天然胜出。**

---

#### 真正的风险：两边都可能被淘汰

- **QA 的风险**：如果只会"点点点"式的手工测试，或者只会套用现有测试框架，
  Agent 会直接替代这部分工作。
  
- **研发的风险**：如果只会"让功能跑通"，不具备系统性质疑 Agent 输出的能力，
  会变成 Agent 的"人肉橡皮图章"，判断价值为零。

---

#### 谁更有潜力胜任？

> **有破坏性思维 + 愿意深入技术底层的 QA，潜力更大。**

原因：

1. Benchmark 设计的核心是**找到系统的边界和失效点**，这是 QA 的本能
2. 研发的思维惯性是"构建"，QA 的思维惯性是"质疑"——后者在 Eval 设计中更值钱
3. 但前提是 QA 必须突破"黑盒测试"的舒适区，深入到 Agent 执行链路的理解

**一句话：QA 的思维方式更匹配，但需要补研发的技术深度。**

反过来，研发补 QA 的思维方式，难度更大——因为这涉及思维习惯的改变，不只是学技术。

---

### Part 2：系统边界设计能力——技术上到底要深入到哪一层？

上一轮确实说得太抽象，直接拆开来说。

#### 具体需要掌握的技术层次

**① Agent 执行链路的内部机制（必须懂，不能黑盒）**

```
用户输入
   ↓
Planning（任务拆解）   ← 要懂：ReAct、CoT、ToT 的差异和适用场景
   ↓
Tool Selection        ← 要懂：工具描述如何影响 LLM 的选择决策
   ↓
Tool Execution        ← 要懂：工具返回结果如何被 LLM 解读和误解
   ↓
Memory/State          ← 要懂：短期上下文 vs 长期存储的边界在哪里
   ↓
Output Generation     ← 要懂：输出结构如何影响下游系统的消费
```

不需要实现每一层，但必须能在每一层上**判断 Agent 的决策是否合理**。

**② 多 Agent 协作的拓扑结构**

需要深入理解的不是框架 API，而是：

```
串行 Pipeline        适合：强依赖、顺序明确的任务
并行 Fanout          适合：独立子任务、结果聚合
层级（Orchestrator） 适合：复杂任务的动态分配
辩论/投票（Debate）  适合：高风险决策的交叉验证
```

技术深度要求：**能判断在你的业务场景里，哪种拓扑会在什么条件下崩溃。**

不是会配置框架，而是能预判失效。

**③ 上下文边界的工程处理**

这是最容易被忽视但最实际的技术点：

- Token 预算管理：长任务中如何决定哪些历史信息该压缩、该丢弃、该保留
- 状态一致性：多 Agent 共享状态时的冲突处理
- 工具调用的幂等性设计：Agent 重试时不能产生副作用（比如重复下单）

**这要求同时懂 LLM 的上下文机制 + 分布式系统的基本原则。**

**④ Human-in-the-loop 的触发机制设计**

技术上具体到：

```python
# 不是这种粗糙的设计
if agent_confidence < 0.7:
    ask_human()

# 而是要能设计这种层次
if task.risk_level == "HIGH" and agent.step_count > threshold:
    # 在哪个执行节点暂停？
    # 给人看哪些信息？（执行轨迹？中间结果？置信度分布？）

> **技术是门槛，经验是壁垒。**

| | 技术 | 经验 |
|--|------|------|

**具体到系统边界设计：**

两者缺一不可，但如果只能选一个方向投资：

> **优先在真实生产环境中部署 Agent 并观察失效，而不是在实验室里研究框架。**

失效案例的积累速度，决定判断力的建立速度。
看一百篇论文，不如一个真实崩溃的 postmortem 有价值。

### AI 自动评估，技术上的可能性路径

不是不可能，已经有苗头：

**现在已经存在的自动评估形态：**
```
AlphaCode    → AI 生成代码 + 自动跑测试用例验证
SWE-Bench    → AI 修复 Bug + 自动验证是否通过原有测试
LLM-as-Judge → 用另一个 LLM 评估 LLM 的输出质量

```

**未来可能的演进：**
```
当前：AI生成 → 人评估
近期：AI生成 → AI初评 → 人审核
中期：AI生成 → AI评估 → AI迭代 → 人设定目标函数
远期：AI生成 → AI评估 → AI迭代 → AI重新定义目标函数？
```

最后一步是真正的跃迁点，也是最大的问号。

---

### 核心障碍：评估的本质是价值判断，不是技术判断

这里有一个根本性的哲学问题：

> **"好代码"的标准，从哪里来？**

```
可测量的部分（AI可以自动评估）：
├── 测试通过率
├── 性能指标
├── 安全漏洞扫描
├── 代码复杂度
└── 与需求文档的符合度

不可测量的部分（目前仍需要人）：
├── 这个需求本身是否值得实现？
├── 这个架构决策在3年后是否会成为债务？
├── 这个功能对用户是否真的有价值？
└── 这个系统的边界划定是否符合业务演化方向？
```

**AI 可以评估"做没做对"，但"做的是不是正确的事"，标准本身需要有人来赋予。**

但——你可以继续追问：**如果 AI 足够智能，能不能自己推导出"正确的事"是什么？**

这就触碰到了 AI 对齐问题（Alignment），不是纯技术问题，是哲学 + 技术的混合难题。

---

### 程序员消亡论：历史规律 vs 这次的不同

**历史规律：每次工具革命，都有人预言程序员消亡**

```
1960s  汇编→高级语言    "不需要懂机器码的程序员了"
1980s  IDE出现          "编程会变得人人可做"
2000s  开源框架爆发     "不需要从零造轮子了"
2010s  低代码平台       "业务人员可以自己开发了"
2020s  Copilot出现      "程序员要失业了"
```

**每次结果：岗位数量反而增加，但工作内容升级。**

---

### 但这次可能真的不同

过去的工具革命，提升的是**执行效率**，人仍然是**思维主体**。

Agentic AI 的本质不同在于：**它开始替代的是思维过程本身，不只是执行。**

```
Copilot：  人思考 → AI辅助执行
Agent：    人定义目标 → AI思考 + 执行
未来Agent：人表达意图 → AI定义目标 + 思考 + 执行 + 评估
```

如果第三阶段成立，程序员的角色会发生根本性转变：

---

### 三种未来场景（不是非此即彼）

**场景A：岗位大幅缩减，但不消亡（概率最高）**

现在100个程序员做的事

**场景B：岗位形态彻底重构（概率中等）**

```
"程序员"这个职位消失
→ 但出现新职位：AI系统设计师、意图工程师、AI审计员
→ 类比：马车夫消失了，但汽车司机、交通工程师出现了
→ 总就业量不一定减少，但技能要求断层式跃升
```

**场景C：AI实现真正自主闭环（概率低，但不为零）**

```
AI自己定义需求 → 自己构建 → 自己评估 → 自己迭代
→ 人只需要表达"我要一个让用户满意的产品"

```

而是：

目前看，有几个锚点是相对稳固的：

| 锚点 | 原因 |
|------|------|
| **意图的模糊性** | 人类的真实需求往往连自己都说不清楚，AI 无法凭空推断 |
| **责任归属** | 系统出错时，需要有人承担法律和道德责任，AI 不能承担 |
| **价值取舍** | 在多个"都对"的方案中做选择，本质是价值观判断 |

最危险的不是 AI 变强，而是：**用旧的职业预期，规划正在发生范式转移的未来。**

## Android 研发工程师的未来方向

---

### 先回应：偏底层是否更难替代？

**部分正确，但需要拆分。**

"底层"不是一个铁板一块的概念：

| 底层类型 | AI 替代难度 | 原因 |
|---------|-----------|------|
| 算法实现（排序、数据结构） | **容易替代** | 有标准答案，AI 已经做得很好 |
| 系统调用、驱动层 | **中等** | 代码量少但上下文复杂，AI 理解硬件约束能力弱 |
| 性能调优、内存管理 | **较难替代** | 需要大量运行时观察经验，不是静态代码问题 |
| 架构设计、系统边界 | **难替代** | 前面讨论过，价值判断 + 经验积累 |
| 硬件 × 软件交叉（BSP、HAL） | **最难替代** | 物理世界约束，AI 训练数据稀少 |

所以底层 ≠ 安全，**关键是这个底层工作是否高度依赖真实硬件环境的经验积累。**

---

### Android 研发的处境

先说一个不太好听的判断：

> **纯应用层的 Android 研发，是 AI 替代压力最大的方向之一。**

原因：
- 代码模式高度重复（Activity、Fragment、ViewModel、Repository……）
- 大量训练数据公开存在（GitHub 上海量 Android 代码）
- Jetpack Compose 的声明式范式，比命令式更容易被 AI 生成

但 Android 生态本身很宽，不是只有应用层。

### 可选方向分析

#### 方向一：Android 系统层 / Framework 层
**替代难度：高**

```
AOSP Framework 开发
├── AMS/WMS/PMS 等系统服务
├── Binder 机制深度定制
├── 厂商 ROM 定制（高通/MTK 平台）
└── HAL 层开发
```

为什么难替代：
- 需要同时理解 Linux Kernel + Android Framework + 硬件约束
- 出问题时的 debug 高度依赖真机环境和经验
- 训练数据相对稀少（大量是厂商私有代码）

**适合人群**：愿意深入 C/C++ + Java 双栈，对操作系统原理有兴趣的人

---

#### 方向二：性能工程 / 稳定性工程
**替代难度：较高**

```
├── 启动速度优化（冷启动/热启动）
├── 内存优化（OOM、内存泄漏、GC 压力）
├── 渲染性能（卡顿、掉帧、过度绘制）
├── 电量优化
└── Crash/ANR 治理体系
```

为什么有价值：
- 性能问题的根因分析，高度依赖**运行时数据 + 经验判断**
- 不是写代码的问题，是**诊断和决策**的问题
- 需要建立监控体系、度量标准——这正是前面说的 Eval/Harness 能力在 Android 场景的映射

> 这个方向和前面讨论的 Benchmark 设计能力，有很强的迁移性。

---

#### 方向三：Android × AI 的交叉方向
**替代难度：低（短期），壁垒建立期**

```
├── 端侧模型部署（TFLite、ONNX Runtime、MediaPipe）
├── NPU/GPU 加速（高通 QNN、MTK APU）
├── 端侧推理优化（量化、剪枝、算子融合）
└── 端云协同架构设计
```

为什么值得投资：
- AI 端侧化是确定性趋势（隐私、延迟、成本驱动）
- 需要同时懂 Android 系统层 + ML 模型特性，复合壁垒
- 目前人才稀缺，供需缺口大

**风险**：这个方向变化快，需要持续学习投入。

---

#### 方向四：开发者工具 / 工程效能
**替代难度：中等，但方向有意思**

```
├── Android 构建系统优化（Gradle、AGP 深度定制）
├── 自动化测试框架设计（Espresso、UIAutomator、自研）
├── CI/CD 流水线 for Android（多渠道、多设备矩阵）
└── Android Lint 规则 / 静态分析工具开发

- 这就是 Android 场景下的 **Harness Engineering**
- 自动化测试框架设计 = Eval 框架设计在移动端的具体形态
- 如果 AI Agent 未来负责写 Android 代码，**谁来设计验证 Agent 输出的框架？** 这个方向的人。

---

#### 方向五：向上走——技术产品 / 架构
**替代难度：高，但需要转型**

```
├── 移动端架构师（跨团队技术决策）
├── 技术 TL（带人 + 做系统设计）
└── 技术产品经理（懂 Android 技术的 PM）
```

这不是纯技术方向，但对于资深 Android 研发，
**技术深度 + 业务判断力的组合**，是 AI 最难替代的形态。

---

### 综合建议

不同阶段的侧重：

```
现在
├── 如果在应用层    → 尽快向性能工程 或 Android×AI 方向延伸
├── 如果在系统层    → 继续深耕，同时补 AI 端侧知识
└── 如果做工程效能  → 主动拥抱 Agent 时代的 Harness 角色

3–5年后
└── 无论哪个方向，"能定义质量标准 + 判断 AI 输出是否可信"
    会成为比"写代码"更核心的竞争力
```

> 不做任何方向延伸，等着看 AI 发展。
