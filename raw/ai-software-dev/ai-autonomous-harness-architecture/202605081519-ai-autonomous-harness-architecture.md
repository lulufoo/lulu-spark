## 问题一：这篇文章讲了一件什么事

**一句话**：这篇文章讲的是——当你要让 AI 自主完成一个**耗时很长、超出单次上下文窗口**的复杂软件开发任务时，应该怎么设计"脚手架"（Harness）来让它能持续、稳定地干活。

---

## 问题二：按段落解读原文思想

### 第一段：背景与动机

**核心矛盾**：AI 模型的上下文窗口是有限的，但真实的应用开发任务可能需要几小时甚至几天。让 AI 一口气完成是不现实的。最初的粗糙做法是让 Agent 单次"梭哈"，结果是：跑到一半上下文满了，任务要么烂尾，要么下一个会话完全不知道前一个干了什么。

**思想**：这不只是工程细节问题，而是一个**系统架构问题**——如何让 AI 跨越上下文边界、持续工作。

---

### 第二段：两 Agent 的初步方案

引入了两个角色的分工：

| 角色 | 职责 |
|---|---|
| **Initializer（初始化 Agent）** | 拆解任务、建立特性清单、初始化环境和进度文件 |
| **Coding Agent（编码 Agent）** | 每次会话只做一个特性，完成后更新进度，交棒给下一次 |

**思想**：模仿人类团队交班的方式——每个人接手时都有一份明确的"待办 + 进度"文档，不需要靠记忆接续。这解决了上下文断裂问题，但还不够，因为"做出来"不代表"做对了"。

---

### 第三段：核心突破——Generator + Evaluator（生成-评估双 Agent）

灵感来自 GAN（生成对抗网络）：

- **Planner**：把用户的一句话需求扩展成完整的产品规格（特性列表 + 技术方向）。
- **Generator**：按 Sprint 逐步实现特性，编码前先与 Evaluator 协商"Sprint Contract"（明确的验收标准）。
- **Evaluator**：用浏览器自动化工具（如 Playwright）真实操作运行中的应用，像 QA 工程师一样测试，而不是只看代码。

**思想**：把主观的"好不好"转变成客观可评分的测试项。这是关键——让 AI 系统能**自我验证**，而不依赖人类每步确认。

---

### 第四段：Sprint Contract——"做之前先定好怎么算赢"

Generator 和 Evaluator 在编码开始前，协商出一份**可测试的验收条件**（类似用户故事的 AC），例如：
> "矩形填充工具：点击拖拽可用选定的瓦片填充矩形区域。"

**思想**：这是把软件工程的**契约式设计**（Design by Contract）嫁接进 AI 工作流。防止了"完成了但不对"的情况，也防止了评估标准随意变动。

---

### 第五段：持久化与上下文管理

核心工件：
- `feature_list.json`：全局特性状态记录
- `claude-progress.txt`：当前进度日志
- **Git 版本控制**：既是时间线，也是状态恢复的锚点

**思想**：记忆的问题，用**外置存储**解决，而不依赖模型本身的上下文。这让"任意长时间的任务"在工程上成为可能。

---

### 第六段：并行扩展与结论

对于更大的任务（比如 Anthropic 另一篇文章提到的"让多个 Claude 并行写 C 编译器"），进一步引入：
- **并行 Agent**：多个 Generator 同时开发不同模块
- **任务分发与协调机制**：类似工厂流水线的调度

**思想**：Harness 设计不是一次性的 prompt 优化，而是一套**可扩展的软件架构范式**，将 AI 从"工具"升级为"半自治的工程协作方"。

---

**一个值得质疑的点**：文章的评估方式（Evaluator 用 Playwright 测试）在 UI 驱动的 Web 应用上有效，但对于非 UI 类任务（如算法库、数据管道），这套框架的适用性需要更多论证，文章对此涉及较少。

## 一、Planner 如何拆分任务让功能不相互干扰？

这是这篇文章**真正没有回答清楚的地方**——你的质疑是对的。

文章的描述停留在"Planner 把需求拆成特性列表"这个层面，但对于**如何避免跨任务的文件冲突**，原文几乎没有展开。

从更广泛的资料来看，目前社区和 Anthropic 实践里的做法大概是：

| 策略 | 说明 |
|---|---|
| **按功能模块划分，而不是按文件划分** | 每个 Sprint 对应一个独立的业务功能（如"用户登录"、"商品列表"），由 Planner 在设计阶段尽量保证功能边界对应文件边界 |
| **顺序执行，不并行冲突文件** | 如果两个特性都要改同一个核心文件（如路由表、主入口），Planner 将它们排成串行队列，先完成一个再做下一个 |
| **Git 作为隔离机制** | 每个 Sprint 在独立分支进行，合并时检测冲突，由 Evaluator 或人工处理 |
| **共享文件优先完成** | 架构性的共用文件（数据库模型、路由配置）放在最早的 Sprint 里完成，后续 Sprint 只在其上添加，不修改 |

你说的"交叉文件太多就不拆分"这个思路本质上是对的，但**Planner 并没有一套严格的自动化冲突检测算法**（至少原文没有描述）。它依赖的是：
1. 模型本身的规划能力（靠 prompt + 推理来尽量设计出低耦合的拆分方式）
2. Git + 顺序执行来兜底

这是目前这套方案**尚未解决得很优雅的问题**。

## 二、Planner/Generator/Evaluator 最终是不是都以 Agent 为载体？

**是的。** 三者本质上都是"一个 Claude 模型实例 + 一套 System Prompt + 工具集"的组合，即：

```
Agent = 模型调用 + System Prompt（角色定义）+ 工具权限
```

- Planner Agent：被赋予"把需求变成规格说明"的角色，工具可能只是写文件
- Generator Agent：被赋予"编写代码"的角色，工具包括读写文件、运行命令
- Evaluator Agent：被赋予"测试验收"的角色，工具包括 Playwright、浏览器自动化

三者是**同一个模型（Claude）的不同实例化**，通过不同的 prompt 和工具赋予不同职责。

---

## 三、这篇文章描述的是"Claude Code 之上的开发者设计"，还是"Claude Code 内部已经做完了"？

**明确结论：这是写给开发者看的外部架构设计指南，不是在介绍 Claude Code 的内置功能。**

层次关系如下：

```
用户/开发者
    ↓ 编写
Harness（脚手架代码）—— 这篇文章讲的就是这一层的设计
    ↓ 调用
Claude Code（或 Claude API + Agent SDK）—— 执行层
    ↓ 驱动
Claude 模型 —— 推理层
```

这篇文章的读者是**想用 Claude Code 做复杂长时间任务的工程师**，告诉他们应该在 Claude Code 之上再架一层 Harness，而不是裸用。

Claude Code 本身提供的是：工具调用、文件读写、运行 shell 命令、基本的上下文压缩（compaction）。

Harness 提供的是：多 Agent 协调、任务拆分、进度持久化、Sprint 流程控制。**这些是开发者自己要写的。**

---

## 四、"Planner 将用户一句话扩展成产品规格"——这是 Claude Code 做的，还是上层规约让 Claude Code 做的？

**是上层规约（Harness 的 prompt）驱动 Claude Code 去做的，Claude Code 本身不自动做这件事。**

具体流程是：

1. 开发者写一个 **Planner Agent 的 System Prompt**，例如："你是一个产品规划师，请把以下用户需求扩展为完整的功能列表，输出为 JSON 格式，写入 feature_list.json"
2. 把用户的原始需求作为 user message 传入
3. Claude（通过 Claude Code 或 API）执行这个 prompt，输出结构化的产品规格
4. Harness 代码读取这份规格，再驱动 Generator Agent 开始按特性列表编码

所以"Planner 的智能"来自 Claude 模型，但**"Planner 这个角色的存在"是开发者通过 Harness 设计出来的**，Claude Code 不会自动扮演 Planner。

## 核心矛盾：边界定义本身就是最难的那一步

你说"如果系统外部交互都定义清楚了，生成需求也不是不可能"——这句话是对的，但它等价于说：

> **"如果困难的部分已经解决了，剩下的部分就不难了。"**

在大型公司里，**"定义清楚系统边界和上下游依赖"这件事本身**，恰恰是最难的、最依赖人的、最容易烂尾的部分。原因：

1. **边界是动态的**：系统边界会随着组织架构、业务优先级、技术债迁移而变化，没有一份静态文档能长期准确描述它
2. **上下游依赖是隐性的**：很多依赖不体现在接口文档里，而体现在"老员工的脑子里"、"线上监控的告警规则里"、"历史事故的复盘文档里"
3. **跨部门的知识天然不流通**：你说的这一点是现实，业务知识不在文档里，在人际网络里

所以你的最终结论可以更精确地表述为：

> Planner 流程驱动，**只在系统边界已经被人显式定义清楚的前提下才可行**。而"把边界定义清楚"这件事，本身就是一项产品工程能力，不是 AI 能自动完成的。

---

## 现实研发里实际是什么情况

现实里有三种层次的团队，面对这个问题的处境完全不同：

| 团队层次 | 边界清晰度 | AI 驱动需求生成的可行性 |
|---|---|---|
| **小型产品团队 / 独立系统** | 高，通常一个人全懂 | 可行，Planner 流程能用 |
| **中型公司，系统有明确服务边界（如微服务 + 接口文档）** | 中，接口清晰但业务规则隐性 | 部分可行，需人工补充业务约束 |
| **大型公司，跨部门、多年历史系统** | 低，边界模糊、文档腐烂 | 基本不可行，Planner 会产生幻觉式需求 |

Anthropic 文章描述的场景，其实更接近**第一种**——一个全新应用、边界清晰、没有历史包袱。这也是为什么那套流程在论文和演示里看起来很美，但落地到真实企业系统时会遇到你说的这些问题。

## 我的判断

你前面的担忧（现实与虚拟的割裂、隐性知识无法文档化）**没有被推翻，只是被推后了**。

更准确的分层是：

```
第一层（人的职责，AI 暂时无法替代）：
  → 定义系统边界
  → 识别上下游依赖
  → 沉淀隐性业务规则为显性约束

第二层（AI 可以承担，Planner 流程有效的范围）：
  → 在边界已定义的前提下，扩展需求细节
  → 生成验收标准
  → 拆分 Sprint 任务
  → 检测任务间的文件/接口冲突
```

所以你真正推翻的，不是"Planner 不现实"这个担忧，而是推翻了"Planner 必须从零开始理解一切"这个错误预设。**Planner 不需要理解一切，它只需要在一个被人清晰定义过的局部范围内工作。**

这个结论其实对 AI 工具的落地策略有很直接的指导意义：**AI 能力的边界，和人把知识显式化的能力边界是同一条线。**

## 你描述的是一个真实的博弈均衡

改一行代码，要走完整条链路：
```
口头沟通 → 产品边界文档 → 技术文档 → 需求评审 → 代码变更
```

理性人的选择必然是：**直接改代码，事后补一句注释，或者什么都不补。**

这不是人懒，这是**合理的成本收益判断**。流程的收益（可追溯、可复现）远小于成本（多方协调、文档同步），于是流程被绕过，隐性知识继续隐性。

这个均衡是稳定的，强制打破它的代价极高。

---

## 但这里有一个值得质疑的隐含假设

你的推论链是：

> 隐性知识显性化成本太高 → 流程驱动不现实 → AI 驱动的 Planner 落地困难

这个链条我基本同意，但有一个地方值得拆开看：

**"显性化"不等于"文档化"。**

传统流程要求的显性化路径是：**人写文档 → 文档驱动系统**。这条路确实太重。

但还有另一条路：**系统行为本身就是知识的载体**。

- 接口的实际调用关系（可以从流量/链路追踪里挖）
- 代码的变更历史（谁改了什么、为什么）
- 线上告警规则（隐含着业务边界的防御性定义）
- IM 沟通记录（那句"一句话沟通"其实是存在的，只是没有结构化）

这些东西不是"文档"，但它们是**结构化程度不同的隐性知识的痕迹**。

AI 能做的，可能不是"驱动人把知识写进文档"，而是**从这些痕迹里逆向提取知识**。

## 现实研发的真实分层

我觉得现实里知识存在三个层次，AI 当前能渗透的深度不同：

| 知识层次 | 存在形态 | AI 当前能力 |
|---|---|---|
| **显性知识** | 需求文档、接口文档、注释 | 可以直接消费和生成 |
| **半显性知识** | Git commit、链路追踪、告警规则、PR 描述 | 可以提取，但噪音大 |
