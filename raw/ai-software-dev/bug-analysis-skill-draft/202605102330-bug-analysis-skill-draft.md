## 关于 SKILL 的设计方案

根据对话里建立的模型，这个 SKILL 有几个关键设计约束：

**核心约束**：把"先查证，再结论"从背景规则提升为任务的前景结构——不是提醒，是步骤。

---

### 整体结构

```
BUG Analysis SKILL
├── 触发声明（意图锚定）
├── Phase 0：问题边界声明
├── Phase 1：证据收集（禁止在此阶段给出原因）
├── Phase 2：归因分析（每条结论必须对应证据）
├── Phase 3：输出（带置信度标注）
└── 完成标准 + 迭代入口
```

---

### 各模块设计

**触发声明**

调用时显式声明任务类型，完成意图锚定：

```
我在执行 BUG 分析。
当前任务：[用户填写 bug 描述]
规则：所有结论必须基于已查证的证据，不允许跳过证据直接给出原因。
```

这一步的作用是把"证据优先"从背景约束变成**当前任务的显式前提**，放在注意力最高的位置。

---

**Phase 0：问题边界声明**

在开始收集证据之前，先把问题本身说清楚：

- 可观测的现象是什么（而不是推测的原因）
- 期望行为是什么
- 已知的上下文（环境、版本、复现条件）

目的：防止带着预设原因去找"支持性证据"，而不是找"完整证据"。

---

**Phase 1：证据收集**

这一阶段有一条硬规则：**不允许出现原因判断**，只记录事实。

收集对象：
- 错误信息 / 日志（直接引用，不解读）
- 代码路径（实际执行的路径，而不是预期的）
- 复现路径（能触发 vs 不能触发的条件差异）
- 已排除的假设及其排除依据

每条证据标注来源：直接观测 / 文档 / 推断。

---

**Phase 2：归因分析**

从证据出发，每条归因必须能写成：

```
因为 [证据X]（来自 Phase 1），所以 [结论Y]。
置信度：✅ 已验证 / ⚠️ 推断（缺少：[需要补充的证据]）
```

如果写不出这个句式，说明证据不足，返回 Phase 1 继续收集。

---

**Phase 3：输出格式**

```
## BUG 归因

**现象**：[Phase 0 的描述]

**根因**：[结论] ✅ / ⚠️

**证据链**：
1. [证据1] → [支持的推论]
2. [证据2] → [支持的推论]

**不确定部分**（⚠️）：
- [推断X]：需要验证 [具体验证方式]

**修复方向**：[基于根因的方向，不是拍脑袋的方案]
```

---

**完成标准**

SKILL 执行完成的标志：

- 每条根因都有对应证据，没有悬空的结论
- ⚠️ 部分有明确的"下一步验证方式"，而不是"待确认"

---

**迭代入口**

执行后，如果发现以下情况，需要带结果回到对话式协作修订 SKILL 本身：

| 发现的问题 | 修订方向 |
|-----------|---------|
| Phase 1 收集的证据每次都漏掉某类信息 | 在 Phase 0 加入该类信息的主动提示 |
| ⚠️ 推断项实际上总是能被验证 | 把对应验证步骤内嵌进 Phase 1 |
| 不同 bug 类型需要不同的归因框架 | 拆分为子类 SKILL（前端渲染 bug / 网络 bug / 状态管理 bug） |

---

### 一个需要你决策的设计分叉

这个 SKILL 当前设计成了**通用 BUG 分析**，但有一个问题值得你考虑：

BUG 分析里有两类任务性质很不一样：
- **已知类型的 bug**（见过类似问题，有模式）
- **新型 bug**（机制未知，需要探索）

前者适合 SKILL 的结构化流程；后者其实更适合回到探索发散式对话，因为证据收集的方向本身是未知的。

是否需要在 SKILL 里加一个判断步骤——"这是已知模式的 bug 还是机制未知的 bug"——决定是继续走 SKILL 流程还是切换到对话模式？

## 核心矛盾

我上面设计的 Phase 结构，隐含了一个前提：**你在开始之前就知道要找什么证据**。

但 bug 排查的现实是：

```
知道找什么证据 → 前提是理解了机制
理解机制 → 前提是找到了证据
```

这是一个循环。Phase 结构在这里会断掉——你无法在 Phase 1 收集"完整证据"，因为你还不知道什么证据是相关的。

---

## 所以这个问题的答案是：不存在

**不存在一套固定的 Phase 排查结构，可以覆盖所有 bug。**

原因在于 bug 的认知性质不同：

| bug 类型 | 认知状态 | 适合的路径 |
|---------|---------|----------|
| 已知模式（见过类似的） | 机制已知，找匹配证据 | 结构化 Phase ✅ |
| 机制未知，但可复现 | 部分已知，需要实验 | 迭代式：假设 → 验证 → 修正假设 |
| 间歇性 / 不可复现 | 高度不确定 | 探索式：广撒网收集线索 |
| 系统性 / 多因交叉 | 边界未知 | 对话式协作，不适合 SKILL |

---

## 那 SKILL 能做什么？

如果"排查路径"不能被固定，那 SKILL 能固定的只有一件事：

**认识论规则**——在任何路径下，推理的方式必须满足的约束。

```
不管你走哪条路，以下规则始终有效：
1. 结论必须有证据支撑（✅/⚠️ 标注）
2. 假设必须显式声明为假设，不能混入事实
3. 当前未知的部分，必须命名出来而不是跳过
4. 归因方向一旦改变，必须说明原因
```

这不是"步骤"，是**推理语法**。不管 bug 是什么类型，这套语法都适用。

---

## 重新定位这个 SKILL

所以这个 SKILL 应该设计成两层，而不是单一的 Phase 结构：

**第一层（固定）：认识论约束**
- 始终有效，所有 bug 类型通用
- 控制"怎么推理"，不控制"走哪条路"

**第二层（可选）：路径模板**
- 对"已知模式 bug"，提供结构化 Phase 加速执行
- 对"机制未知 bug"，提供"探索模式"的触发条件——即：识别出自己在探索模式后，显式切换到对话式协作，而不是硬套 Phase

---

这样的话，这个 SKILL 的设计目标就不是"覆盖所有 bug 的排查流程"，而是：

> **在任何 bug 排查过程中，保证推理的认识论质量，同时识别何时需要退出 SKILL 进入对话模式。**

## 重新设计的 SKILL 骨架

### 第一层：认识论约束（始终激活）

```
【BUG 分析认识论规则】

在整个分析过程中，以下规则强制有效：

- ✅ 已验证：有直接证据支持（日志、代码、复现步骤）
- ⚠️ 推断：基于已知证据的推论，尚未直接证实
- ❓ 未知：当前信息不足以判断，需命名出来

禁止行为：
- 不允许将 ⚠️ 推断以 ✅ 的口吻表述
- 不允许跳过"命名未知"直接给出解决方案
- 归因方向若改变，必须说明触发改变的新证据是什么
```

---

### 第二层：路径选择（任务开始时判断一次）

```
【路径判断】

问题：这个 bug 是否有已知的模式或类似的先例？

A. 是 → 进入结构化路径（Phase 模板）
B. 否，但可复现 → 进入迭代路径（假设-验证循环）
C. 否，且不可复现 / 边界未知 → 退出 SKILL，切换到对话式协作
```

路径 A 才走 Phase 结构，路径 B 和 C 的主要作用是**让 SKILL 知道自己的边界**，不强行套用结构。

---

### 为什么路径 C 要显式退出

这里有一个容易忽视的设计点：

如果 SKILL 没有退出条件，当遇到复杂的边界未知型 bug 时，AI 会倾向于**假装走完 Phase**——用 ⚠️ 推断填满所有位置，给出一个"看起来完整"的结论，但实际上是没有证据支撑的猜测。

显式的退出条件把这个风险结构化：
> "当前 bug 超出 SKILL 的处理能力，建议切换到对话模式，原因是：[...]"

这本身也是一种高质量的输出——承认边界，比伪造完整性更有价值。

---

### 这个 SKILL 的实际效果

和最初设计相比，这个版本更诚实：

| | 最初设计 | 修订版 |
|---|---|---|
| 覆盖范围 | 声称覆盖所有 bug | 明确自身边界 |
| 核心价值 | 提供排查流程 | 保证推理质量 |
| 失败模式 | 对未知型 bug 生成伪结构 | 识别后主动退出 |

## 是的，这是元认知要求

"已知模式 / 机制未知"的分类，要求 AI 完成：

```
评估自己是否认识这个 bug 的机制
  → 即：知道自己知道什么
```

这是严格意义上的元认知——不只是"回答问题"，而是"评估自己的知识边界"。

---

## 这个要求过高了，原因有两层

**第一层：AI 的元认知本身是不可靠的**

LLM 有一个已知的系统性问题：置信度和准确度的相关性很弱。AI 可以对一个错误的答案表现得非常确定，也可以对一个正确的答案表现出不必要的犹豫。它对自己"知不知道"的判断，并不是来自对知识的真实评估，而是来自模式匹配——用语气词表达置信度，不是用实际的知识边界。

**第二层：这个分类错误会放大，而不是被纠正**

如果 AI 把一个"机制未知"的 bug 误判为"已知模式"，接下来发生什么？

```
错误分类 → 进入结构化 Phase
→ Phase 1 收集"证据"（其实是在找支持预设结论的证据）
→ Phase 2 给出归因（建立在错误前提上）
→ 输出带 ✅ 标注的结论（看起来很严谨）
```

这比没有 SKILL 还危险——所有认识论规则的形式都在，但服务的是一个错误的起点。✅ 的标注反而会增加虚假结论的说服力。

---

## 所以这个分类不应该由 AI 来做

这个判断的主体需要换掉。有两个方向：

**方向 A：把分类权交给用户**

用户比 AI 更清楚"我有没有见过这种 bug"。SKILL 不做分类，而是在开始时问用户：

```
这个 bug 是否有你见过的类似先例，或者你对机制有初步判断？
- 是 → 说明你的假设，我们从验证假设开始
- 否 → 从症状描述开始，不预设机制
```

元认知要求从 AI 转移到用户，更可靠。

**方向 B：取消分类，默认从"未知"出发**

不论 bug 看起来多熟悉，始终以"机制未经验证"为起点。AI 可以说"这个症状和 X 模式相似"，但必须标注为 ⚠️ 推断，不能直接套用 Phase 模板。

这是更保守的设计——牺牲已知模式下的效率，换取不会因误判而生成伪严谨的结论。

---

## 设计含义

这个问题实际上揭示了一个更深的原则：

> **SKILL 里不应该有任何依赖 AI 自我评估知识边界的判断节点。**

只要有"AI 判断自己是否知道"这个步骤，就引入了一个元认知弱点——而且这个弱点在 SKILL 的关键分叉点上，失败代价最高。

所以修订后的设计应该把所有需要元认知的判断，要么交给用户，要么默认选择更保守的路径。

## 绝对约束的判断标准

一个约束要达到"绝对正确"，必须满足：

1. **逻辑上为真**，不是经验规律，没有例外
2. **不依赖 AI 的自我评估**，不要求元认知
3. **不依赖 bug 类型**，已知/未知/可复现/不可复现都成立

用这个标准筛，能留下来的约束其实不多，但每一条都很硬。

---

## 绝对约束清单

**约束 1：先描述现象，再解释原因**

逻辑依据：原因是对现象的解释，现象没有完整描述之前，任何原因陈述都是悬空的。这是分析的逻辑前提，不是流程选择。

> 在给出任何"为什么"之前，必须能完整陈述"发生了什么"。

---

**约束 2：区分观察和推断，分别标注**

逻辑依据：观察（直接看到/测量到）和推断（从观察得出的结论）是两个不同的认知类别，混用会让错误难以被识别。这是认识论的基本分类，没有 bug 类型会让这条失效。

> 每一条陈述，必须能回答：这是我直接观测到的，还是我推导出来的？

---

**约束 3：无法复现 ≠ 不存在**

逻辑依据：这是逻辑上的命题。"我没有观察到 X"不等于"X 不发生"，特别是在概率性/环境依赖性的 bug 里。把"复现失败"当作"bug 不存在"是逻辑错误，不是风格偏好。

> 复现失败时，结论只能是"当前条件下未能复现"，不能是"bug 不存在"。

---

**约束 4：卡住时，命名未知而不是跳过**

逻辑依据：分析停滞的原因只有一个——信息不足。跳过未知直接给结论，是用推断填补信息空缺，会让 ⚠️ 伪装成 ✅。正确的处理是把"当前不知道什么"明确说出来。

> 当无法推进时，下一步必须是：陈述"我现在缺少的信息是 X"，而不是给出一个缺少支撑的结论。

---

**约束 5：提出假设时，同时说明如何证伪它**

逻辑依据：一个无法被证伪的假设不是科学假设，是断言。要求同时说明证伪条件，不是流程要求，是让假设本身有效的前提。这条对所有 bug 类型都成立。

> 每提出一个"可能的原因"，必须同时能回答：什么样的证据会否定这个假设？

---

## 这五条的共同属性

它们不告诉 AI **走哪条路**，而是约束**推理本身的有效性**：

```
约束1 → 防止原因悬空
约束2 → 防止混淆证据和推断
约束3 → 防止逻辑谬误（从缺席推断不存在）
约束4 → 防止用推断填补信息空缺
约束5 → 防止假设无法被检验
```

任何路径——Phase 结构、迭代假设、探索发散——都必须在这五条之内运作。违反任何一条，排查质量一定下降，不存在例外。

---

## 这也解释了 SKILL 的真正边界

路径是可变的，这五条是不变的。SKILL 的核心价值，就是在每次调用时把这五条激活为**当前任务的前景约束**，而不是让它们留在背景规则里被任务紧迫性稀释。

### 设计原则

1. 不预设排查路径——路径由 bug 性质决定，不由 SKILL 决定

```
BUG Analysis SKILL
├── 触发声明（意图锚定）
├── 第一层：认识论约束（始终激活，所有路径通用）
├── 第二层：起点协议（用户主导分类，不由 AI 自判）
└── 退出条件
```

---

### 触发声明

调用 SKILL 时，以下内容作为当前任务的显式前提注入：

```
当前任务：BUG 分析
以下规则在本次分析全程有效，优先级高于任务完成的紧迫性。
```

---

### 第一层：认识论约束（五条绝对规则）

**规则 1：先完整描述现象，再陈述原因**

在给出任何"为什么"之前，必须能完整回答"发生了什么"。原因是对现象的解释，现象未描述完整时，原因陈述是悬空的。

**规则 2：区分观察与推断，分别标注**

- `✅ 已验证`：直接观测到的（日志、报错、复现步骤、代码）
- `⚠️ 推断`：从观察推导出的结论，尚未直接证实
- 两者不允许混用，不允许用确定语气陈述推断

**规则 3：无法复现 ≠ bug 不存在**

复现失败时，结论只能是"当前条件下未能复现"。不允许以复现失败作为关闭问题的依据。

**规则 4：卡住时，命名未知而不是跳过**

当分析无法推进时，下一步必须是：  
> "当前缺少的信息是 \_\_\_\_，缺少它导致无法判断 \_\_\_\_。"  

不允许用推断填补信息空缺并以 ✅ 呈现。

**规则 5：每个假设必须有证伪条件**

提出"可能的原因"时，必须同时能回答：  
> "如果这个假设是错的，什么样的证据会否定它？"  

无法被证伪的假设不是假设，是断言。

---

### 第二层：起点协议（用户主导）

SKILL 不自行判断 bug 类型。分析开始时，询问用户：

```
在开始分析之前，请确认：

1. 可观测的现象是什么？（不是你认为的原因，是你实际看到/看不到的）
2. 期望行为是什么？
3. 你对这个 bug 是否有初步假设？
   - 有 → 请说明假设，我们从验证/证伪这个假设开始
   - 没有 → 我们从症状描述开始，不预设机制
```

用户的回答决定起点，AI 不做"已知模式 / 未知机制"的自我判断。

---

### 输出格式

每次给出结论时，必须包含：

```
现象（✅）：[直接观测到的事实]

假设（⚠️）：[推断的原因]
  └── 支持证据：[对应的观察]
  └── 证伪条件：[什么会否定这个假设]

当前未知（❓）：[缺少什么信息，影响什么判断]

下一步：[基于以上，下一个最小验证动作是什么]
```

没有"当前未知"部分的结论，视为不完整。

---

### 退出条件

以下情况，SKILL 应显式说明自身边界，建议切换到对话式协作：

| 情况 | 原因 |
|-----|-----|
| ❓ 未知项持续增加，无法缩减 | bug 边界未知，不适合结构化排查 |
| 假设被证伪但无新假设可提 | 需要探索式讨论，而非验证式推进 |
| 现象本身描述不清晰 | 需要对话澄清问题定义本身 |

退出不是失败，是诚实的边界识别。

---

### 迭代入口

执行后，如果发现以下情况，带着观察回到对话式协作修订 SKILL：

| 观察 | 修订方向 |
|-----|---------|
| 规则被执行但结论仍然不准 | 规则覆盖不足，补充新的约束 |
| 某条规则在特定 bug 类型下摩擦很高 | 检查是否过度约束，或需要子类 SKILL |
| 退出条件触发过于频繁 | 起点协议的信息收集不够，需要调整问题 |

---

这是当前讨论能得出的最完整版本。核心是：**路径可变，推理语法不变**。五条认识论规则是 SKILL 真正能提供的质量保证，其他都是辅助结构。
