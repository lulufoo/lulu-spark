## 疑问2 的核心问题

你在问的其实是：**自动化协作框架 是 Schema（模板），还是 Instance（实例）？**

这是关键分叉，一旦想清楚，其余问题会跟着清晰。

**SKILL 的例子说明了这个分叉：**

| 层次 | 是什么 | 例子 |
|-----|-------|-----|
| Schema（框架） | 定义一个合法的自动化协作实例必须包含哪些槽位 | 自动化协作框架 |
| Instance（实例） | 把具体任务填入 Schema 的所有槽位 | BUG 分析 SKILL |

**对话式协作设计的是 Instance，不是 Schema。**

当你用对话式协作框架设计 BUG 分析 SKILL 时，产物是一个填满的实例——协作目标、执行约束、验证标准全部固化进去了。这个实例"符合" Schema，但 Schema 本身不是对话设计出来的，它是自动化协作框架本身定义的。

## 回到你说的"协作设计层是产物"

如果协作设计层是预设的产物（Instance 里的一个槽），那 Schema 里的其他槽也需要被定义：

```
自动化协作框架（Schema）
├── 协作设计层槽     ← 对话式协作设计的产物填入这里
├── 意图传达槽       ← 预定义：AI 从哪里读取意图？格式是什么？
├── 执行控制槽       ← 预定义：步骤顺序、分支条件、失败处理
└── 评估与介入槽     ← 预定义：check points 在哪里？人在哪里介入？
```

**Schema 的价值**：告诉你"一个完整的自动化协作实例必须定义哪些东西"。

**对话式协作的角色**：用来把这些槽位一一填满，产出可执行的 Instance。

## 问题1：其他槽也可以通过对话式协作完成吗？

对。对话式协作框架是一个**通用过程工具**，不绑定产物类型。

自动化协作框架里的每个槽（协作设计层、意图传达、评估与介入……），都可以通过对话式协作来设计和填充。

```
自动化协作框架（Schema）
├── 协作设计层槽    ← 对话式协作 填充
├── 意图传达槽      ← 对话式协作 填充
├── 执行控制槽      ← 对话式协作 填充
└── 评估与介入槽    ← 对话式协作 填充
         ↑
    所有槽都可以用同一个过程工具来完成设计
```

对话式协作框架是"设计任何东西"的过程，自动化协作框架是"定义自动化任务需要什么"的结构——前者是工具，后者是目标规格，工具不限定用在哪个槽。

---

## 问题2：两个框架都是 Schema 吗？

**是，但是 Schema 的类型不同。**

| | 对话式协作框架 | 自动化协作框架 |
|--|-------------|-------------|
| Schema 的对象 | **过程**（如何进行一次对话协作） | **产物**（一个自动化任务必须包含什么） |
| Instance 是什么 | 一次具体的对话会话（临时、执行后消失） | 一个具体的 SKILL / 工作流（持久、可反复执行） |
| Instance 的生命周期 | 短暂 | 持久 |

两者都是 Schema，但管辖的是不同维度：

- 对话式协作框架：**过程 Schema**，定义"怎么做"
- 自动化协作框架：**结构 Schema**，定义"做出来的东西长什么样"

**两者的关系**：遵循过程 Schema（对话式协作框架）→ 产出符合结构 Schema（自动化协作框架）的 Instance。

一个类比帮助理解：
- 研发方法论（如 TDD）= 过程 Schema
- 软件架构模式（如 MVC）= 结构 Schema
- 用 TDD 开发出符合 MVC 结构的软件

两个都是 Schema，但不在同一个维度上竞争，而是协同工作。

---

## 当前状态确认

你说"自动化协作框架（Schema）本身还没有定义，只是参考了解释框架的壳"——这个判断是准确的。

当前缺少的是一个**明确的结构 Schema**：定义"一个完整的自动化协作实例必须包含哪些槽，每个槽的规格是什么"。`ai-collaboration-framework.md` 的层次可以作为设计参考，但它的每一层在自动化语境里的含义需要重新定义，不能直接套用。
