### Q1：语音识别是三方 SDK 还是自研？

**结论：接入第三方 SDK，非自研。**

官方隐私政策明确列出：使用**腾讯云实时语音识别 SDK**。技术上是 WebSocket 流式传输音频 → 云端识别 → 返回文字，实现"边说边出字"效果。

---

### Q2：语音识别做到了什么层次？情绪/语气有处理吗？

**已实现层次**

| 能力 | 状态 |
|---|---|
| 语音 → 文字（ASR） | ✅ 已实现 |
| 多语言识别（30种）| ✅ 已实现 |
| 多声纹识别（最多5人）| ✅ 已实现 |
| 口语润色（去结巴/语气词）| ✅ LLM 后处理 |
| 智能摘要 | ✅ LLM 后处理 |

**情绪识别层次**

腾讯云 ASR 提供情绪识别能力（参数 `emotion_recognition`，识别高兴/伤心/愤怒，增值付费项）。但 Get笔记 隐私政策中该 SDK 用途仅列为"语音转文字"，产品界面也无情绪标签展示，大概率未开启情绪识别增值项。

语气/语义理解由 LLM 层（Doubao/Qwen/GLM）后处理实现，不是 ASR 层能力。

**结论**：当前产品停留在"语音→干净文字→智能摘要"链路，情绪识别能力底层有支撑但产品层未开启。

### Q4：智能总结是怎么做的？

**标准的 ASR → 文本 → LLM Prompt 流水线**

```
[用户语音]
  → 腾讯云 ASR（流式转写 + 声纹分离）
  → 原始文字稿（带说话人标注）
  → Get笔记后端（存储 + Embedding）
  → LLM API（Doubao/Qwen/GLM 三选一）
  → 智能摘要/润色结果 → 用户
```

三家 LLM 并存，推断是 A/B 测试 + 降级容灾双重策略。不同场景用不同 Prompt：短录音→润色，长录音/会议→结构化摘要（要点+决策+行动项）。

AI 搜索是典型 RAG：笔记做 Embedding → 向量检索 → 组装 Prompt → LLM 回答。

**总体判断**：技术自研深度较浅，语音识别+大模型均为采购云服务，核心竞争力在产品体验和场景设计。

## AI（Turn 3）

查证了两个关键变量：三家 LLM 的上下文窗口（阿里云官方文档 2026-04-27）和腾讯云 ASR 的输出结构。

---

### 结论先行：这个问题对 Get笔记 的场景基本不存在

原因是两层保障叠加。

---

### 第一层：上下文窗口已远大于场景需求

✅ 已验证，来源：阿里云文档（2026-04-27）

| 模型 | 上下文窗口 |
|---|---|
| Qwen3.6-plus / flash | 1,000,000 tokens（约70万汉字）|
| GLM-5.1 | 198,000 tokens |
| Doubao 系列 | 128k～256k tokens |

实际会议录音文本量估算：
```
中文语速：约150字/分钟（正常会议节奏）
1小时会议 → 约 9,000 字 → 约 13,500 tokens
2小时会议 → 约 18,000 字 → 约 27,000 tokens
8小时工作日全录 → 约 72,000 字 → 约 108,000 tokens
```

即使用上下文最短的 GLM（198k tokens），也能完整放入连续8小时的会议文字。用 Qwen 的1M窗口，相当于可以放70本小说。Get笔记的典型场景对这些模型来说根本不是问题，不需要 Chunk。

---

### 第二层：ASR 输出天然提供句级边界

✅ 已验证，来源：腾讯云 ASR API 文档

腾讯云 ASR 返回的是按说话停顿自动分句的结构化数据：

```json
{
  "slice_type": 2,
  "start_time": 0,
  "end_time": 2840,
  "voice_text_str": "这次会议的主要议题是..."
}
```

每一个 `slice_type=2` 是一个自然句子的完整结束。文本天然按语义句子切分好，每个切片是一个完整的语句。如果真的需要分段处理，切割点只会落在句子边界，而不是文字中间。主题撕裂问题在输入端就已经被规避了。

---

### 真正需要 Chunking 的极端场景

⚠️ 推断（逻辑推导）：

唯一可能触发 Chunking 的是超长导入文件（如8小时以上完整课程录音）。如果真到这一步，工程上最自然的处理方式是 Map-Reduce 摘要：

```
按 ASR 句子边界 + 静音停顿点切割
  → 每段独立 LLM 摘要（Map 阶段）
  → 多段摘要拼合再送 LLM 汇总（Reduce 阶段）
```

由于切割点落在 ASR 给定的自然句子边界，跨主题撕裂概率极低。

---

### 一句话总结

Get笔记的场景下，Chunking 问题几乎不存在：①LLM 上下文窗口（最大1M tokens）远超任何正常录音的文字量；②ASR 输出本身就是按自然句子分段的结构化文本，切割边界天然对齐语义。"主题被拆到不同 Chunk 导致摘要混乱"这个问题，是在用固定字数强行切割纯文本时才会出现，Get笔记的架构从源头就绕开了这个坑。

### 第一层：原型级别——其实很简单

核心链路只有三段：

```
ASR SDK（WebSocket，约30行代码）
  → LLM API（HTTP POST，约20行代码）
  → 本地存储（任意方案）
```

现有云服务把技术门槛砍到极低。一个有经验的独立开发者，一个周末可以做出能用的原型。所有重的部分（声学模型、大语言模型）都已经是按量付费的 API。

---

### 第二层：真正的难点，按严重程度排序

**难点一：流式体验的编排（技术复杂度最高）**

Get笔记的核心体验是"边说边出字"，但隐藏了一个调度难题：

```
用户说话
  → ASR 实时返回【不稳定结果】（字还在变）
  → ASR 最终返回【稳态结果】（一句话定稿）
  → 这时候再调 LLM 润色
  → LLM 返回结果
```

问题在于这条链路是串行的，每个节点都有延迟。如果等 ASR 稳态→等 LLM 返回，用户会感受到明显停顿感。想让整体体验"丝滑"，需要同时处理：ASR 结果在变时怎么预处理、LLM 调用何时触发、结果怎么流式展示、上下文怎么管理。这是细节工程，说不清楚但做出来才知道难。

**难点二：Prompt 精调的工程量（持续时间最长）**

这不是"一个技术难题解决完就好"，而是持续的迭代工作。Get笔记至少有几类文本处理场景，每类需要独立的 Prompt 策略：

| 场景 | 期望行为 |
|---|---|
| 碎片想法（10秒）| 润色但保留原意，不能"改写" |
| 会议录音（1小时）| 要点/决策/行动项三段式结构 |
| 学习课程 | 章节化，核心概念提取 |
| 随手记 | 保留个人风格，不要过度书面化 |

同一个"总结"Prompt，用在想法记录上会显得过于正式，用在会议上又可能漏掉关键细节。每类场景调好 Prompt 之后，还会碰到边界 case——夹杂中英文、专有名词、途中打岔停顿又继续。这类工程量没有尽头，是持续投入而非一次性解决。

**难点三：iOS 后台录音限制（平台限制，绕不开）**

iOS 特有的硬约束：
- 后台录音：App 切到后台，iOS 会挂起音频采集，除非申请特定 Background Mode（`audio`），而且还不能滥用，否则被 App Store 拒审
- 系统内录：iOS 没有开放系统音频采集的公开 API，"手机内录"功能在 iOS 上通常依赖 ReplayKit，限制很多
- 长时间录音的内存/电量管理：录2小时会议要保证 App 不被系统杀掉、音频文件分片写入、断点续传

个人开发者在这里最容易碰壁：本地测试跑通了，一到真实场景（息屏、切 App）就出问题。

**难点四：专有名词的 ASR 准确率（长尾问题）**

腾讯云 ASR 通用模型对日常语言准确率高，但用户各自行业的专有词汇是个长尾问题：公司名/产品名/人名（"张三丰"被识别成"张三风"）、技术术语、英文缩写夹杂中文时的断句混乱。腾讯云提供热词表功能，但谁来维护每个用户的热词表是个产品难题。

**难点五：长文摘要的"中间段质量"问题**

即使上下文窗口足够大，LLM 对输入中间位置内容的注意力会衰减（业界称 "Lost in the Middle" 问题），导致长会议中 30～60 分钟那段的要点容易被遗漏。不知道这个问题的话，摘要效果会莫名在特定位置有质量落差，很难 debug。

| 最值得投入的地方 | Prompt 工程（直接决定输出质量，是真正的差异化）|
| 最容易踩坑的地方 | iOS 后台限制 + ASR 专有名词 |

**一句话**：这个 App 的技术难点不在"能不能做出来"，而在"能不能做得好用"。核心竞争力是 Prompt 调优的积累，而不是底层技术。个人做出来玩没问题，做成真正好用的产品需要大量用户反馈驱动的迭代。
