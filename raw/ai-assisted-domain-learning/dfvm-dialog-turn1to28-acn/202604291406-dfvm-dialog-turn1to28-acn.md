## 框架 vs 事实的操作定义

| 维度 | 框架 | 事实 |
|---|---|---|
| 本质 | 领域的**不变结构**——任何从业者必须回答的核心问题集合 | 填充框架槽位的**可变内容** |
| 时效性 | 相对稳定 | 持续更新 |
| 认知负荷 | 低（骨架轻） | 高（细节重） |
| 迁移性 | 强（跨域通用） | 弱（领域专属） |

芒格的核心主张：**先建槽位，再填充内容**。没有槽位的事实是散沙，有了框架的事实才是知识。

## 系统如何操作

### 现有系统的默认行为（问题所在）
```
用户问 → 系统输出内容 → 用户记忆内容
```
问题：内容落地无处挂载，用户不知道"这个知识放在哪个抽屉"。

### 框架优先的系统行为
```
用户进入领域
  → Step 1: 系统先检查/构建框架（不给内容）
  → Step 2: 框架确认后，按槽位填充内容
  → Step 3: 遇到新事实，先定位槽位，再输入
```
关键操作：**在给出任何内容前，先问"你用什么框架组织这个领域？"**

## 快速搭建默认领域框架（不深入事实）

任何领域，5个维度可以快速生成骨架：

### 维度1：定位（What）
- 这个领域解决什么**核心问题**？
- 不解决什么？（边界）
- 与哪些领域相邻/交叉？

### 维度2：机制（Why/How）
- 领域内部的**核心因果链**是什么？
- 有哪些不可违背的基本规律？（类比物理定律）

### 维度3：角色（Who）
- 有哪些关键**行动者**？
- 各自的激励结构是什么？

### 维度4：工具箱（Tools）
- 从业者用什么**核心方法/工具**做决策？
- 哪些工具是必须掌握的最小集合？

### 维度5：层级与演化（Levels）
- 这个领域有哪些**抽象层次**？（微观/中观/宏观）
- 历史上经历了哪些**范式转移**？（了解结构变化，不是历史细节）

---

## 具体执行流程

以"Java并发编程"为例，框架搭建不超过30分钟：

**不做**：直接读 synchronized 原理、AQS 源码

**做**：
1. 定位 → 并发解决什么问题？（多线程共享资源的安全与效率矛盾）
2. 机制 → 核心矛盾是什么？（可见性/原子性/有序性三要素）
3. 角色 → 谁在协作？（线程、锁、内存模型、调度器）
4. 工具箱 → 解法分几类？（互斥/不变性/隔离/CAS）
5. 层级 → 有哪几层抽象？（语言层/JVM层/硬件层）

框架建完后，再遇到任何并发事实（如 volatile 语义、ConcurrentHashMap 实现），都能先定位槽位，再挂载。

## 深度报告的设计原则

**TPM 可以借鉴的**：动态分类逻辑（领域类型 × 学习目的 → 选不同结构）

**TPM 不能用的**：槽位选择逻辑（TPM 会省略维度，深度报告不能）

深度报告的核心设计原则是：

> **全量槽位 + 动态权重**，而非 TPM 的"按目的选视角"

## 全量槽位系统（7层）

这是深度领域报告的固定骨架，所有领域都要覆盖：
```
Layer 1  定位层       核心问题定义 / 边界 / 邻域接口
Layer 2  概念层       基本概念体系 / 分类结构 / 核心假设
Layer 3  机制层       核心规律 / 因果结构 / 反馈环路
Layer 4  方法层       核心方法 / 决策框架 / 评估标准
Layer 5  实践层       典型问题模式 / 已知失效模式 / 边界案例
Layer 6  演化层       历史范式转移 / 当前前沿 / 活跃争议
Layer 7  元层         与其他领域的借鉴/输出关系
```
---

## 动态权重：按领域类型分配

| 领域类型 | 核心加权层 | 次要层 | 可轻量处理 |
|---|---|---|---|
| **机制型**（物理/经济） | L2 概念、L3 机制 | L4 方法、L5 实践 | L7 元层 |
| **工程型**（软件/医学） | L4 方法、L5 实践 | L2 概念、L3 机制 | L6 演化（只要范式背景）|
| **系统型**（生态/组织） | L3 反馈、L2 角色分类 | L5 涌现现象 | L4 方法（工具较少）|
| **规范型**（法律/伦理） | L2 定义、L5 例外与边界 | L6 演化（规则如何形成）| L3 机制（较轻）|
| **描述型**（分类/史学） | L2 分类体系 | L6 演化 | L3/L4（机制和方法较弱）|

**权重的实际含义**：

- **核心加权层**：必须深度展开，是该领域推理的基础
- **次要层**：必须覆盖，但不是主要骨架
- **可轻量处理**：有基础即可，不是认知杠杆点

## 两种动态的本质差异

**动态修正**（Correction）= 框架的**结构**发生变化
> 例：最初把 Java 并发归类为"工程型"，深入后发现"机制型"才是主结构，L3 层的分组需要调整

**局部放大**（Magnification）= 框架的**深度**发生变化
> 例：框架已经完整，但想把 L3（机制层）从"基础覆盖"扩展到"深度展开"

两者不同在于：修正改变框架骨架，放大只是在骨架内加细节。

---

## L1 定位层

### 核心问题

异步/并发编程有两个根本矛盾：
1. **回调地狱**：多层嵌套回调导致代码结构与执行顺序分离，逻辑难以追踪
2. **线程资源瓶颈**：JVM 线程由 OS 管理，每个线程约需数 MB 内存，通常只能支撑数千个并发线程

Kotlin 协程的核心答案：**以挂起替代阻塞**——让代码在等待时主动释放线程，而非让线程被动等待，从而用少量线程支撑大量并发任务，同时保持顺序化的代码书写风格。

### 领域边界

| 属于本领域 | 不属于本领域 |
|---|---|
| suspend 函数与挂起机制 | OS 级线程管理（协程运行在线程上） |
| CoroutineScope / CoroutineContext | Java 标准库线程 API（ExecutorService 等） |
| 结构化并发（父子生命周期） | 具体框架集成（Android Lifecycle, Ktor 路由） |
| 协程构建器（launch / async / flow） | 跨进程通信（网络协议、IPC） |
| Flow / Channel / SharedFlow / StateFlow | 内存模型与 JVM 底层调度 |
| 取消与异常传播机制 | |

### 邻域接口

| 关系 | 领域/技术 | 接口说明 |
|---|---|---|
| 上游依赖 | JVM 线程模型 | 协程最终运行在线程上，Dispatcher 管理这层映射 |
| 上游依赖 | Kotlin 语言编译器 | suspend 关键字是语言特性，编译器负责 CPS 变换 |
| 竞争/互补 | RxJava / Reactor | 同解异步问题，响应式 vs 协程式；Flow 部分重叠 |

| 设计借鉴来源 | Go goroutines | 轻量并发单元的思路来源之一 |
| 设计借鉴来源 | C# / JS async-await | suspend 函数语法的参考来源 |

## L2 概念层

### 概念分组

**Group 1：基础单元**

| 概念 | 定义 |
|---|---|
| **suspend 函数** | 用 `suspend` 关键字标注的函数；可在不阻塞线程的情况下暂停执行；只能在另一个 suspend 函数或协程中调用 |
| **协程（Coroutine）** | 可被挂起和恢复的计算实例；不是线程；是比线程更轻量的并发单元（50,000 个协程 ≈ 500MB，同数量线程 ≈ 100GB） |
| **续体（Continuation）** | 协程被挂起时保存的状态快照；记录"下一步从哪里继续执行"；协程可挂起/恢复的底层机制 |

**Group 2：执行容器**

| 概念 | 定义 |
|---|---|
| **CoroutineScope** | 协程的生命周期容器；所有协程必须在某个 Scope 内启动；Scope 结束时，其内所有协程递归取消 |
| **CoroutineContext** | 类似 Map 的元素集合，定义协程的行为属性（包含 Job + Dispatcher + ExceptionHandler 等）；从父协程继承 |
| **Job** | 协程的生命周期句柄；状态：Active → Completing → Completed，或 Active → Cancelling → Cancelled |

**Group 3：调度**

| 概念 | 适用场景 |
|---|---|
| `Dispatchers.Default` | CPU 密集型计算；共享线程池，大小 = CPU 核数 |
| `Dispatchers.IO` | I/O 操作；更大线程池（默认 64 或 CPU 核数，取较大值） |
| `Dispatchers.Main` | UI 线程（Android/Swing/JavaFX 等平台特定） |
| `Dispatchers.Unconfined` | 不限定线程；恢复时在调用线程执行（慎用）|

**Group 4：构建器**

| 构建器 | 用途 | 返回值 |
|---|---|---|
| `launch {}` | fire-and-forget，只关心副作用 | Job |
| `async {}` | 需要获取计算结果时使用，配合 `.await()` | Deferred\<T\> |
| `coroutineScope {}` | 创建子作用域，等待所有子协程完成；子协程失败则取消所有兄弟 | T（挂起）|
| `supervisorScope {}` | 同上，但子协程失败不影响其他兄弟 | T（挂起）|
| `runBlocking {}` | 非挂起代码调用挂起代码的桥梁；**阻塞当前线程**；生产代码慎用 | T（阻塞）|

**Group 5：通信与流**

| 概念 | 冷/热 | 生产者-消费者关系 | 典型用途 |
|---|---|---|---|
| **Flow** | 冷 | 一对一；有消费才生产 | 数据流处理、替代 RxJava 大多数场景 |
| **Channel** | 热 | 一对一；每个值只送达一个消费者 | 协程间点对点通信 |
| **SharedFlow** | 热 | 一对多；所有活跃收集者都收到每个值 | 事件广播 |
| **StateFlow** | 热 | 一对多；持有最新值 | UI 状态管理（替代 LiveData）|

### 核心假设

1. **结构化并发**：每个协程必须归属于某个 Scope；父子生命周期强绑定；不允许"游离"协程
2. **协作式取消**：取消不是强制中断，协程在挂起点主动检测取消状态（`CancellationException`）
3. **线程无关性**：协程可在一个线程挂起，在另一个线程恢复；代码不应假设"当前线程不变"

## L3 机制层

**编译器变换（CPS Transform）**：编译器将 suspend 函数转换为状态机。每个挂起点是一个状态，每次恢复从对应状态继续执行。这是协程不需要特殊 JVM 运行时支持的原因。

**线程释放机制**：当协程调用 `delay()` 等挂起函数时，线程不被阻塞，立即返回给线程池处理其他协程。`delay(1000ms)` 期间，该线程可运行数千个其他协程的逻辑。

**结构化并发的实现**：每个子协程的 Job 都链接到父 Job。父取消 → 向所有子协程传播 `CancellationException` → 递归取消。父等待子完成后才完成自身（`coroutineScope` 语义）。

**异常传播差异**：`launch` 中的未捕获异常立即传播到父 Job 并触发取消；`async` 中的异常被存储在 `Deferred` 中，直到调用 `.await()` 时才抛出——这是两者最重要的行为差异。

> 状态：⬜ 基础覆盖

---

## L4 方法层

**选择构建器**：有结果用 `async/await`，无结果用 `launch`；需要桥接阻塞代码用 `runBlocking`（仅在最外层或测试中）。

**切换调度器**：`withContext(Dispatchers.IO) { ... }` 在不创建新协程的情况下切换执行线程；常用于在计算密集型和 I/O 密集型操作间切换。

**Flow 操作链**：`flow { emit(value) }` 构建 → `map/filter/transform` 变换 → `collect` 终止。冷流特性意味着每次 `collect` 都重新执行生产逻辑。

**异常处理**：`CoroutineExceptionHandler` 处理 `launch` 顶层未捕获异常；`supervisorScope` 隔离子协程故障；`try/catch` 在挂起函数内正常工作。

> 状态：⬜ 基础覆盖

### 缺陷一：各视角产出的内容类型没有区分

当前模型定义视角的方式是：**哪几层强制深展**。

但是，强制深展 L2 无论在哪个视角下都会产出"概念 + 分组 + 定义" —— 因为没有规定 L2 在不同视角下应该输出**什么类型的内容**。
```

机制视角 L2：理解机制所必须的最小概念集（不是全量分类）
实践视角 L2：决策时需要辨别的概念（不是全量分类）
```
同一层，不同视角，内容类型完全不同。但我的模型没有定义这一层差异，导致各视角输出形态趋同——都长得像知识图谱。

---

### 缺陷二（更根本）：领域类型被放在了错误的轴上

当前设计：
```
轴一：领域类型（工程型/机制型/系统型…）→ 主选视角
轴二：学习目的（认知/实践/迁移）
两轴组合 → 视角原型
```
问题：**领域类型被当作视角选择器，但它不应该是。**

"工程型 × 认知 → 结构视角"——这个规则导致了今天的错误。用户学 Kotlin 协程的认知目标是"挂起机制怎么运作"，这是一个机制问题，但因为 Kotlin 协程被判定为工程型，就被强制映射到结构视角。

领域类型描述的是**领域知识的客观性质**，但视角描述的是**用户想回答什么问题**。这两件事不在同一个维度上，不应该共同决定视角。

---

### 根因

参照 TPM 的设计，再看 DFVM 的设计失误：

| | TPM | DFVM（当前）|
|---|---|---|
| 视角选择器 | 用户目的（单轴，纯主观意图）| 领域类型 × 学习目的（双轴，客观 × 主观）|
| 主体类型的作用 | 不影响视角选择，只影响内容深度（通过用户背景校准）| 直接参与视角选择 |

TPM 之所以稳定：**视角由用户意图单轴决定，主体特性只影响内容，不影响结构。**

DFVM 的问题：**把领域类型放上了视角选择轴，让客观属性覆盖了用户真实意图。**

---

### 正确的设计方向

**领域类型降轴**：从"视角选择轴"降为"层内容修饰符"。
```
视角选择：纯意图驱动（用户想回答什么问题？）
  → 概念架构型（"这个领域由什么组成？如何组织？"）
  → 机制型      （"这个领域怎么运作？为什么？"）
  → 实践型      （"我怎么用这个领域？"）
  → 迁移型      （"这个领域有什么可以带走的原则？"）
  → 演化型      （"这个领域如何演化到今天？"）

领域类型的作用：在选定视角内，调整各层的内容侧重
  → 机制型视角 + 工程型领域：L3 聚焦设计机制和工程取舍
  → 机制型视角 + 系统型领域：L3 聚焦反馈环路和涌现机制
  → 机制型视角 + 规范型领域：L3 聚焦规则执行机制和例外处理
```
这样，今天的错误就不会发生：用户说"怎么运作的" → 机制型视角 → 直接进入；领域是工程型这件事只影响 L3 里谈什么，不改变用视角。

|---|---|
| **收缩** | 某些层降为一句话，甚至允许合并 |

| **重命名** | 按视角语义重命名标题，但保留 L? 编号作为语义锚 |

- 领域类型修饰写在 11 个原子槽上（一次）
- 视角卡片做槽的选取 + 合并 + 重命名
- 输出文档是 4~6 个节，不是 7 个，且每节内容高度对齐视角目的

## 第三层：5 张视角卡片（各自从 11 槽选取、合并、命名）

每张卡片定义：哪些槽强制深展 / 哪些合并成一节 / 哪些跳过。

**结构视角**（知识地图）：
```
节1 [S1]         定位与边界       强制深展
节2 [S2+S3]      概念与分类体系   强制深展
节3 [S4]         核心假设         基础覆盖
节4 [S5+S6]      机制与方法概述   基础覆盖（合并）
节5 [S9+S10]     演化与前沿       基础覆盖（合并）
节6 [S11]        跨域关系地图     强制深展
跳过：S7 S8（实践失效不是结构视角的核心）
```
**机制视角**（因果理解）：
```
节1 [S1]         机制背景         基础覆盖
节2 [S2+S4]      核心概念与假设   强制深展（理解机制的最小集）
节3 [S5]         因果机制         强制深展（完整因果链+条件）
节4 [S8]         失效边界         强制深展（不懂机制会犯的错）
节5 [S6+S7]      推导出的方法论   基础覆盖（合并）
节6 [S11]        跨域溯源         可选
跳过：S3 S9 S10
```
**实践视角**（如何做事）：
```
节1 [S6+S7]      决策工具箱       强制深展（方法+选择标准合并）
节2 [S8]         失效模式库       强制深展
节3 [S5]         机制约束         基础覆盖（选择背后的逻辑）
节4 [S2]         关键概念辨别     基础覆盖
节5 [S1]         背景             基础覆盖（一句话）
跳过：S3 S4 S9 S10 S11
```
**迁移视角**（可带走什么）：
```
节1 [S5]         可迁移规律       强制深展（从机制层提炼抽象原则）
节2 [S4+S1]      原则成立条件     基础覆盖（假设前提+问题背景）
节3 [S11]        跨域共鸣与应用   强制深展

```
**演化视角**（如何变迁）：
```
节1 [S9]         演化时间线       强制深展

节3 [S1+S2]      当前形态溯源     基础覆盖（今天的样子从哪来）
节4 [S11]        对外影响链       基础覆盖
跳过：S3 S4 S6 S7 S8
```

## 这个方案的效果

**输出文档的变化**：

机制视角框架从 7 节 → 6 节，节的名称变成"机制背景 / 核心概念与假设 / 因果机制 / 失效边界 / 推导出的方法论 / 跨域溯源"，而不是"L1 定位层 / L2 概念层 / ..."——读起来天然贴合认知目的。

**模型文档的变化**：

当前节 4~7 的内容，重构为：
- 11 槽定义表（11 行）
- 领域类型修饰表（5 行）
- 5 张视角卡片（各 6~8 行）

总量与现在相当，但逻辑层次清晰：槽 → 修饰 → 视角选取。

---

## 最诚实的代价

这个设计有一个真实成本：**设计者需要对 11 个原子槽有清晰认知**，才能保证视角卡片的选取不遗漏、不重叠。当前的 7 层更容易"直觉性"执行，11 槽需要更严格的定义。

模型的质量上限高了，但执行门槛也高了一些。
