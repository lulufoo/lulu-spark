现在我要组织这份文档的结构，涵盖从共享状态协调的必要性、线程与锁的机制、内存模型的基础、同步语义链路，一直到并发工具框架、策略权衡、失控模式和虚拟线程等前沿话题。

Java 的设计初衷就是支持并发编程，所有执行都在线程上下文中进行，多个独立线程可以访问同一对象，因此程序员必须确保线程间的读写访问被正确协调——通过同步机制保证对象在同一时刻只被一个线程修改，防止线程在另一线程修改期间读到部分更新的对象。JVM 的线程模型允许多条线程并发执行，这些线程虽然独立运行，但共享内存空间。

如果没有正确的同步，程序行为会变得难以预测，这正是并发编程领域存在的根本问题所在。这一节的核心是解决如何在并发访问下维护对象状态的一致性和可见性，使多线程程序的行为符合规范预期。

现在我来看看线程、锁和并发工具的整体架构——线程通过 `java.lang.Thread` 类创建，调用 `start()` 方法启动；Java 中每个对象都有一个监视器，同一时刻只有一个线程能持有该监视器的锁，`synchronized` 语句通过对对象的监视器进行加锁来实现同步。

除了 `synchronized` 外，`volatile` 变量和 `java.util.concurrent` 包中的类也提供了替代的同步机制；这个包包含了并发编程中常用的框架和工具，其中包括 `locks` 子包等多个模块。

现在我来看一下这个包的主要组件，按照 Oracle 文档的分类来组织，包括 Executors 框架及其相关的接口和服务。

接下来是 Queues 部分，涵盖了非阻塞队列如 `ConcurrentLinkedQueue` 和 `ConcurrentLinkedDeque`，以及各种阻塞队列实现，还有支持生产者-消费者交互的 `TransferQueue` 和 `LinkedTransferQueue`。

然后是时间单位的处理、各类同步器如信号量和栅栏，最后是并发集合框架，包括 `ConcurrentHashMap`、跳表实现和写时复制的列表与集合，这些在可伸缩性和遍历一致性上各有权衡。

现在我在查阅 JDK 21 的 `java.util.concurrent` 包文档，理解内存模型的基础——JLS 第 17 章的关键点是它并不规定 JVM 如何调度多线程执行，而是定义了允许出现的行为集合，任何只产生这些允许行为的执行策略都是合法的。编译器和处理器的重排序是实现这一灵活性的核心机制。

编译器和微处理器可以自由地重排指令来优化性能，这在与非同步代码交互时会产生看似矛盾的结果——比如两个线程对共享变量的读写操作在重排后可能呈现单线程视角下"不可能"的执行顺序，但这是内存模型的根本设计，而非缺陷。同时，`Thread.sleep` 和 `Thread.yield` 这两个方法没有同步语义，调用前后编译器不需要将寄存器中的写入同步到主内存。

这意味着一个在循环中读取非 `volatile` 字段并调用 `Thread.sleep` 的程序可能永远无法看到其他线程的更新。此外，JVM 不强制检测死锁，所以在涉及多个对象的锁定场景中需要手动应用死锁规避策略或使用更高层次的锁原语。

现在我来看 happens-before 关系的定义。这是 JLS 中的一个偏序关系，用来保证共享变量的写操作对读操作的可见性——只有当写 happens-before 读时，读才能观察到那次写的结果。`java.util.concurrent` 包的文档明确列出了构成 happens-before 链路的具体操作，比如同一线程内的操作顺序。

监视器的 unlock 会 happens-before 后续的 lock，这通过传递性保证了 unlock 前的所有操作对后续 lock 后的操作可见。volatile 字段的写也 happens-before 该字段的后续读，提供了类似的内存一致性保证但不涉及互斥。线程启动和 join 操作也建立了 happens-before 关系——`Thread.start()` happens-before 新线程中的任何动作，而线程中的所有动作 happens-before 其他线程从 `join()` 成功返回。现在我要看 `java.util.concurrent` 包中的高层构件如何利用这些基础关系。

并发集合、Executor、Future 和各种同步器都通过 happens-before 关系来保证线程间的可见性。放入并发集合的动作 happens-before 另一线程取出元素的动作，向 Executor 提交任务 happens-before 任务执行开始，Future 的异步计算结果通过 `get()` 方法建立了 happens-before 关系，而同步器的释放方法（如 `unlock`、`release`、`countDown`）happens-before 其他线程在同一对象上的获取方法。这些高层构件实际上是在基础的 happens-before 规则之上构建的，向上延伸了内存一致性的保证。 现在看并发工具框架的工程实现——核心是通过 Executors 框架将任务提交与执行策略解耦，同时把并发协调结构化为可组合的部件。`Executor` 接口负责任务执行的抽象，`ExecutorService` 加入生命周期管理和 `Future` 追踪，`ScheduledExecutorService` 则处理延迟和周期调度，而 `ForkJoinPool` 针对分治任务的并行处理。

接下来是队列与生产者—消费者模式的设计——`BlockingQueue` 通过阻塞语义（put 等待空间、take 等待元素）将并发协调内化到数据结构中，`TransferQueue` 进一步支持生产者等待消费者接收的同步点，不同的实现方式（有界、无界、优先级、延迟、零容量）对应不同的生产者—消费者场景。

然后是 Synchronizers 这一类——`Semaphore` 控制并发访问数量，`CountDownLatch` 阻塞直到事件发生，`CyclicBarrier` 提供可重置的多方同步点，`Phaser` 支持分阶段计算与动态成员，`Exchanger` 允许两线程交换对象。最后是时间粒度约定，`TimeUnit` 在包内各处统一时间单位的表示。

关于超时参数，它们的语义是「等待的下限时间」——实现会尽快检测超时，但从检测到线程实际恢复之间没有上限保证。现在我要看看并发策略的选型权衡，Oracle 在包概述中对几个关键对立提供了倾向性的断言。

对于集合的选择，当多线程预期同时访问时，`ConcurrentHashMap` 通常优于 synchronized `HashMap`，`ConcurrentSkipListMap` 优于 synchronized `TreeMap`——"Concurrent" 前缀意味着这些集合是线程安全的，但不受单一排他锁治理，允许任意数量的并发读和大量并发写，而 synchronized 类则适合需要单一锁防止所有访问的场景，代价是可伸缩性下降。

`CopyOnWriteArrayList` 在读取与遍历次数远多于更新次数时更合适。未共享或持有其他锁时访问的集合应选择非同步集合以避免额外同步开销。在 JDK 21 后，虚拟线程作为轻量级、不应被池化的选择，以高并发换取吞吐量提升，特别适合 I/O 密集型任务，但在 CPU 密集型计算中增加线程数可能不会带来收益。

这个框架主要用于权衡取舍，具体的数据结构选型规则需要进一步深入探讨。现在开始看典型的失控模式与安全边界。

死锁、数据竞争和可见性问题是Java并发编程中的核心风险——JVM不保证死锁检测，程序员需要手动避让；数据竞争发生在无同步的读写操作间，允许编译器和处理器重排序，导致结果可能违反直觉；而`sleep`和`yield`这类方法在保证线程安全上也有其局限。

现在看虚假唤醒的问题——线程可能在没有显式通知的情况下被唤醒，所以`wait()`必须放在循环内持续检查条件，而不是假设一次唤醒就意味着条件已满足。

接着是并发集合迭代器的弱一致性特性，它们不会抛出`ConcurrentModificationException`，只保证遍历构造时存在的元素，但不反映后续的修改。

现在转向虚拟线程的讨论，这是JEP 444在JDK 21中正式交付的特性，目标是让简单的thread-per-request服务端应用能以接近最优的硬件利用率扩展，同时保持现有Thread API的兼容性和可观测性。

官方明确指出不会移除平台线程、不会静默迁移应用，也不改变Java的基本并发模型或引入新的数据并行构造。虚拟线程的核心在于它们是Thread实例但不绑定到OS线程，只在执行计算时消费OS线程资源，这样大量虚拟线程可以映射到少量平台线程上。

虚拟线程不是为了加快单个任务的执行速度，而是通过M:N调度实现更高的并发度和吞吐量。从历史来看，Java经历过绿色线程（M:1调度）到平台线程（1:1调度）的演变，虚拟线程代表了回到M:N调度模式的新探索。

这个特性经过JDK 19、20的预览阶段，最终在JDK 21正式发布。与此同时，Structured Concurrency作为配套的高层并发API在JDK 21中以预览形式推出，与虚拟线程协同工作，但目前还不是正式交付的特性。
