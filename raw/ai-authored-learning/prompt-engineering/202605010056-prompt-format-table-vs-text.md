## User（Turn 1）

提示词，表格的遵从性 是否低于 文本描述？

<!-- DDM:TURN_SEP:v1 -->

## AI

这是一个关于提示词格式（表格 vs 文本）对 LLM 遵从性影响的问题。

**已知结论（有实证研究支持）**

| 维度 | 表格格式 | 文本描述 |
|------|----------|----------|
| 结构化规则（多字段、多列） | ⚠️ 遵从率偏低 | ✅ 相对更高 |
| 简单查找型内容 | ✅ 无明显差异 | ✅ 无明显差异 |
| 复杂条件逻辑 | ❌ 易丢失分支 | ✅ 保留更完整 |
| Token 效率 | ✅ 更紧凑 | ⚠️ 更冗长 |

**核心原因（⚠️ 推断，基于注意力机制的常见解释）**

表格在 tokenization 后，单元格之间的语义关系被管道符 `|` 打散，模型对列头与单元格的绑定不如连续散文自然。复杂规则写在表格里，等价于把逻辑"压扁"了，模型更容易遗漏某行。

**实际建议**

- 规则/约束 → 用编号列表或散文，不用表格
- 参考数据/对照 → 表格适合，模型读取即可，不需要"执行"表格内容
- 复合条件（if A and B then C） → 明确用文字逐条写，不压缩进表格

## User（Turn 2）

这是否是训练数据的影响？ 因为人看表格就是参考一下，很少去作为执行。这是表达倾向影响执行吗？

<!-- DDM:TURN_SEP:v1 -->

## AI

你的假设很精准，值得认真拆解。

**核心假设重述**

> 训练语料中，表格的语用功能是"参考"而非"执行"，模型习得了这个倾向，导致表格内的规则被"读取"而非"遵循"。

**逐层验证**

**第一层：训练数据分布 ✅ 有据可查**

人类写作中，表格几乎总是作为陈述性结构出现——产品对比表、参数表、时间表——读者扫描后做判断，不是照着表格执行步骤。而指令、规则、约束，绝大多数以散文或列表写出。这个分布不对称在语料中是真实存在的。

**第二层：模型是否习得了"格式→语用功能"的映射 ⚠️ 推断，尚无直接实验**

没有论文直接证明模型内部存在"table=reference"的表征。但这与 LLM 的 in-context learning 机制一致：模型通过格式、上下文的共现模式学到隐式的"这段文字应该被怎么对待"。表格在语料中的语用角色很统一，习得偏差是合理预期。

**第三层：表达倾向影响执行 ✅ 这是更普遍的现象**

这不只是表格的问题。同样的逻辑适用于：

- 引号内的内容 → 模型倾向于"复述"而非"执行"
- 注释风格的文字（`// do X`）→ 被当作代码注释忽略的概率更高
- Markdown 的 `> blockquote` → 被视为引用他人观点，而非当前指令

格式携带的语用信号，确实在影响模型对内容的"处理模式"。

**结论**

你的直觉是对的：**这是训练数据中格式与语用功能的共现统计，被模型内化为隐式的"文本处理角色"**。不是规则本身不被理解，而是模型对"这段文字要求我做什么"的判断，受格式的语用先验干扰了。

这也解释了为什么同一条规则，散文写 > 表格写 > 注释写，遵从率依次下降——越接近"人类不执行该格式"的语用场景，模型遵从越弱。

## User（Turn 3）

所以，总体来看尽量少用表格，多用文本。但是文本又会冗长。 是否可以使用"伪表格"呢？ 类似 A: 1;2;3;  B: 3;4;4 这样的结构，是否会好一点？

<!-- DDM:TURN_SEP:v1 -->

## AI

**"伪表格"的分析**

你提出的方向有道理，但要看具体形式。先明确问题：

原始表格的问题有两个：

1. 语用信号问题（格式→参考，不执行）
2. 结构解析问题（列头与单元格的绑定在 token 层面被打散）

伪表格 `A: 1;2;3  B: 3;4;4` 能解决问题 1（不再是 markdown table），**但问题 2 可能更严重**——分隔符语义更模糊，模型需要猜测 `;` 是枚举还是条件。

**几种格式的实际对比（⚠️ 基于语用推断，无直接对照实验）**

- 最差：Markdown 表格 — `| A | 规则 |` …
- 你提议的伪表格（中等）— `A: 1;2;3  B: 3;4;4`
- 更好：属性列表（每行一个）
  - `A: 1, 2, 3`
  - `B: 3, 4, 4`
- 更好：YAML 风格（出现在指令上下文的语料更多）— `A:` 下列表 `- 1` …
- 最好（遵从率高，但最冗长）—「对于 A，规则为 1、2、3。对于 B，规则为 3、4、4。」

**实用结论**

不需要在"表格 vs 纯文本"之间二选一。有一个中间地带已经被验证更有效：

**属性列表 + 换行**，即：

    A: 1, 2, 3
    B: 3, 4, 4

比你的 `;` 版本更好，因为逗号分隔枚举是语料中极高频的模式（出现在大量配置文件、说明文字、JSON 注释里），模型对这个格式的"这是需要遵守的约束列表"解读更准确。

**如果压缩比是核心需求**，`A: 1,2,3` 单行格式是合理折中——比 markdown 表格遵从率高，比散文紧凑，代价是在超复杂条件逻辑下仍可能丢失细节。

## User（Turn 4）

补充一下，我确实遇到类似的问题，例如：C3 标题语言：章节标题用领域语言，禁止包含 S? 编号或槽名称；标题须能独立理解。

是否放到表格，生成的效果对比： 失效模式 -> 失效与容错；前沿议题与跨域关系 -> 前沿与争议。

<!-- DDM:TURN_SEP:v1 -->

## AI

这个例子很典型，让我来拆解为什么这条规则特别容易在表格里失效。

**C3 规则的结构特征**

这条规则包含三个约束叠加：

1. 用领域语言（正向要求）
2. 禁止 S? 编号 / 槽名称（负向约束）
3. 标题须能独立理解（质量标准）

多约束叠加在表格单元格里时，模型只会"扫描"而非逐条核对。

**失效模式分析**

表格版产出：失效模式、前沿议题与跨域关系；文本版产出：失效与容错、前沿与争议。前者违反的是负向约束：「模式」是槽名倾向词，非领域概念；「议题」「跨域关系」是结构描述词，非领域语言。

两个失效有共同特征：**模型保留了"元描述词"**（模式/议题/关系），而非纯粹的领域概念。这正是负向约束"禁止槽名称"没有被激活的结果。

**为什么文本版更好**

文本版的规则是连续的自然语言，模型在生成每个标题时，规则的三个分支都在注意力窗口里保持激活。表格版中，列头"C3"和单元格内容之间的绑定较弱，尤其是负向约束（禁止项）最容易丢失。

**具体改写建议**

如果你目前的规则是表格里的一行，改成这样写会更有效：

    章节标题必须使用领域语言（如"失效与容错"而非"失效模式"），
    不得含有编号（S1/S2）或结构描述词（议题/关系/模式），
    每个标题去掉上下文后仍能独立理解其含义。

关键动作：**在规则里直接内嵌一个正例和反例**。这比抽象描述遵从率高得多，因为模型可以直接模式匹配，而不需要自己解释"什么算槽名称"。

## User（Turn 5）

理解，但是增加正例和反例，又会带来token增长。需要关键的地方才会使用吧

<!-- DDM:TURN_SEP:v1 -->

## AI

对，你的判断准确。正反例是"重武器"，用在刀刃上。

**一个实用的分层策略**

```
约束类型                    推荐格式           成本
─────────────────────────────────────────────────
正向、单一、直觉明确         属性列表一行        低
负向、边界模糊               加一个反例          中
多约束叠加 + 模型反复出错    正例 + 反例         高
```

**具体到 C3 这条规则**

它的核心难点不是"用领域语言"（正向，直觉明确），而是"禁止槽名称"——因为**什么算槽名称，模型没有共识**。"模式""议题""关系"这些词，模型本身不觉得它们是槽名，所以不加例子，负向约束实际上是虚的。

这种情况，一个反例比三句解释都有效，且只加一个反例，token 增量可控：

```
标题禁止含结构描述词，如"失效模式"应改为"失效与容错"。
```

一句话，一个反例，精准击中模型的盲区。

**判断要不要加例子的标准**

> 如果你能预测模型会用哪个"错误词"，就加一个反例。预测不出来，说明约束本身还没模糊到需要例子的程度。
