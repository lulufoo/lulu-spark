# 从一次错误的 CAS 实现出发，直到乐观并发 — 要点摘要

> **导航**：[distilled](../../../distilled/common-tech/language/202604240037-java-cas-optimistic-concurrency.md)


## 要点

1. **CAS 单次调用不保证成功，必须配合自旋重试；高冲突时化解冲突而非硬扛**
   `compareAndSet` 只保证比较+交换原子，失败时什么都不做。要用 CAS 保证"最终完成一次自增"必须加 while 自旋重试。高并发持续争用时自旋让 CPU 空转，应从根本上降低争用（如 `LongAdder` 分桶），而不是换"更能抗冲突"的机制。

2. **AtomicReference + 不可变对象：CAS 用引用地址作为"值未被修改"的代理判断**
   多个变量同时更新需要封装成不可变对象，CAS 操作整个引用。不可变是前提条件：若允许原地修改字段，引用不变但内容已改，CAS 会误判为"没人动过"。"同一引用 = 同样内容"是 CAS 代理判断成立的基础。

3. **ABA 问题有害条件精确：对象可变且被复用**
   简单计数/标志的 A→B→A 无害。真正有害的是：同一引用对象内容被修改后又改回（对象池/复用场景），CAS 成功但操作在过时快照上继续执行。Java GC 环境下需对象池才能触发，并非普遍风险。

4. **AtomicStampedReference 通过 Pair 不可变对象 + 单次 CAS 实现原子比较引用+stamp**
   将 reference 和 stamp 打包进不可变 Pair，CAS 操作 Pair 的引用地址。前两个 `==` 检查是快速失败优化，原子性保证仅来自最后一个 `casPair`。版本号递增是调用方的责任，JDK 不强制，这也是实际代码里用得少的原因。
