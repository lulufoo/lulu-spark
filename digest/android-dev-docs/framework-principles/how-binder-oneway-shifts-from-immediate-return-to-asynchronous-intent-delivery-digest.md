# Binder oneway：从"立即返回"到"异步意图投递" — 要点摘要

> **导航**：[distilled](../../../distilled/android-dev-docs/framework-principles/how-binder-oneway-shifts-from-immediate-return-to-asynchronous-intent-delivery-distilled.md)

## 要点

1. **"调用返回"和"服务端处理完成"是三个不同时间点，不能混淆**
   客户端调用返回 / 服务端开始处理 / 服务端处理完成——三者不是同一时刻。`oneway` 返回的是"调用方线程控制权"，不是"服务端处理完成信号"。这个区分建立后，"为什么不适合强依赖结果的流程"和"为什么容易带来时序错觉"才能被准确理解。

2. **时序风险：把"已发送"误当"已生效"**
   连续两次 `oneway` 调用都可能迅速返回，但服务端是排队顺序处理。调用方若以为"前一个 oneway 已返回所以状态已更新"，立刻发起依赖该状态的新动作，会出现竞态或读到旧状态。`oneway` 让调用线程轻松了，但把时序复杂性留给了调用链外的世界。

3. **可靠性边界：不保证无限可靠积压，"总归会处理掉"无天然保证**
   `oneway` 只保证调用方尽快返回，不保证服务端及时处理，也不保证无限积压。当服务端状态复杂、消费速度不足或目标进程处于特殊状态时，请求可能被丢弃或长期延迟。这是设计交换：用同步确认能力换取调用路径上的低阻塞。
